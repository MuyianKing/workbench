## 1. 背景与目标

### 1.1 背景

前端开发者通常同时维护多个项目。每次开发都要重复以下动作：打开资源管理器 / 终端、`cd` 到项目目录、确认使用哪个包管理器、执行 `npm run serve`；打包时再执行 `npm run build`，然后手动打开输出目录查看产物。项目数量一多，重复劳动和时间损耗显著。

### 1.2 目标

做一个桌面端「项目控制台」，集中管理本地前端项目，实现：

1. 一次添加项目目录，长期复用
2. 一键安装依赖、一键启动、一键打包
3. 打包结束后自动打开产物所在的资源管理器目录
4. 应用内实时查看命令输出，可随时停止进程

### 1.3 成功标准

- 添加一个已有项目 ≤ 3 次交互（选目录 → 确认命令映射 → 保存）
- 从打开应用到启动某个项目 ≤ 2 次点击
- 多项目可同时运行，各自日志互不干扰
- 关闭并重启应用后，项目列表、分组、配置全部保留

## 2. 角色与场景

### 2.1 目标用户

同时维护 2 个以上前端项目的开发者（单人本地使用，无需登录、无多人协作）。

### 2.2 核心用户场景

| 编号 | 场景 | 期望结果 |
|---|---|---|
| S1 | 首次使用，添加已有项目 | 选择目录后自动识别包管理器与可用脚本，确认即完成添加 |
| S2 | 日常启动开发服务 | 点卡片「启动」，服务跑起来，日志实时可见 |
| S3 | 首次拉取或依赖变更后 | 点「安装依赖」，等待完成，状态提示成功 |
| S4 | 发布打包 | 点「打包」，结束后自动弹出产物目录 |
| S5 | 同时开发两个项目 | 两个项目的服务同时运行，切换终端 Tab 查看各自日志 |
| S6 | 服务异常 / 端口被占用 | 状态变红并给出可读的错误提示 |
| S7 | 项目多了需要归类 | 创建分组，把项目拖入分组，按分组过滤 |
| S8 | 关闭应用时服务还在跑 | 按设置决定是提示确认还是直接连带停止 |

## 3. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 桌面框架 | Electron | 需要本地文件系统访问与子进程管理能力 |
| 前端框架 | Vue 3（组合式 API + `<script setup>`） | — |
| UI 组件库 | Element Plus | 用户指定 |
| 状态管理 | Pinia | — |
| 构建工具 | Vite + electron-vite | 统一主进程 / 预加载 / 渲染进程的构建与热更新 |
| 语言 | TypeScript | 主进程与渲染进程共用类型定义 |
| 持久化 | 本地 JSON 文件（`app.getPath('userData')/projects.json`） | 数据量小，无需数据库 |
| 子进程 | Node.js `child_process.spawn` | 见 3.1 方案说明 |
| 打包发布 | electron-builder → NSIS 安装包（Windows x64） | — |

### 3.1 子进程方案说明（已决策）

备选方案对比：

| 方案 | 说明 | 结论 |
|---|---|---|
| **spawn + IPC（采用）** | 主进程 `spawn` 启动命令，按行推送 stdout/stderr 到渲染进程日志面板 | 实现直接、可控性强、零原生依赖；日志为纯文本流，非真实 TTY |
| node-pty + xterm.js | 真实伪终端，支持交互式命令 | 需编译原生模块，显著增加打包复杂度，对本产品属过度设计 |
| 调起系统终端窗口 | `start cmd /k npm run serve` | 应用内无日志、无法可靠停止进程，与需求冲突 |

采用第一种。子进程管理封装为独立的 `ProcessManager` 模块，未来若需升级为伪终端，仅替换该模块，渲染层接口不变。

### 4.4 一键操作与进程管理（P0）

| 编号 | 需求 | 优先级 |
|---|---|---|
| F-4.1 | 一键安装依赖：执行安装命令，过程中按钮进入 loading 且不可重复触发 | P0 |
| F-4.2 | 一键启动：执行启动命令，状态置为「运行中」，卡片指示灯变黄 | P0 |
| F-4.3 | 一键打包：执行默认打包命令；按钮带下拉箭头，可从多条打包命令中切换 | P0 |
| F-4.4 | 打包成功后自动打开产物目录（见 4.5）；失败时不打开 | P0 |
| F-4.5 | 停止：终止该项目的进程，状态回到「空闲」 | P0 |
| F-4.6 | 重启：先停止再启动，用于快速应用改动 | P1 |
| F-4.7 | 允许多个项目同时运行，进程之间完全隔离，各自维护独立的日志缓冲与状态 | P0 |
| F-4.8 | 同一项目的同一类操作不允许并发触发（如启动中不能再点打包），按钮置灰 | P0 |
| F-4.9 | 停止进程时需终止整个进程树（Windows 下使用 `taskkill /pid <pid> /T /F`），避免残留子进程占用端口 | P0 |
| F-4.10 | 应用退出时，按设置处理运行中的进程（见 F-8.4） | P0 |

**状态机**

```
idle ──install──> installing ──> idle（成功）/ failed
idle ──start────> running ──stop──> idle
running ──异常退出─> failed
idle ──build────> building ──> success ──> idle（3 秒后自动回到 idle）
building ──失败──> failed
failed ──用户重新操作──> installing / running / building
```

状态与指示灯映射：

| 状态 | 指示灯 | 卡片按钮 |
|---|---|---|
| idle | 灰 | 全部可用 |
| installing | 黄（转圈） | 安装按钮 loading，其余置灰 |
| running | 黄（常亮） | 显示「停止」「重启」 |
| building | 黄（转圈） | 打包按钮 loading，其余置灰 |
| success | 绿（3 秒后自动回到 idle） | 全部可用 |
| failed | 红（常亮，点开看日志） | 全部可用 |

说明：`idle` 即为终态，停止后、成功标记过期后、失败后均回到该状态，不存在单独的 `stopped` 状态。`success` / `failed` 只是 `idle` 之上的临时视觉标记。

## 6. 技术架构

### 6.1 进程职责划分

```
渲染进程 (Vue3 + Element Plus + Pinia)
  ├─ ProjectGrid          项目卡片网格
  ├─ ProjectDrawer        项目详情抽屉
  ├─ TerminalPanel        多 Tab 日志面板
  └─ SettingsView         设置页
        ↕ IPC（preload 通过 contextBridge 暴露白名单 API）
主进程 (Electron)
  ├─ ProjectStore         项目元数据读写与持久化
  ├─ ProjectScanner       读取 package.json、探测命令 / 包管理器 / 输出目录
  ├─ ProcessManager       spawn 子进程、状态机、日志缓冲、停止 / 重启
  └─ SystemService        打开资源管理器、打开浏览器、托盘、快捷键、端口检测
```

### 6.2 关键设计约束

- **安全**：渲染进程 `nodeIntegration: false`、`contextIsolation: true`，所有能力经 preload 白名单 API 暴露
- **参数传递**：执行命令不使用字符串拼接后交给 shell，而是 `spawn(cmd, args, { shell: true })` 且参数来源限定为受信任的 `package.json` 脚本名，避免注入风险
- **模块边界**：`ProcessManager` 只依赖「项目 ID + 命令 + 工作目录」，不感知 UI；`ProjectScanner` 为纯函数式读取，无副作用
- **日志流控**：主进程按行推送，渲染进程按帧批量合并写入，避免高频 IPC 阻塞

### 6.3 数据模型

```ts
interface Project {
  id: string
  name: string                        // 显示名
  path: string                        // 项目根目录绝对路径
  packageManager: 'auto' | 'npm' | 'yarn' | 'pnpm'
  detectedPackageManager: 'npm' | 'yarn' | 'pnpm'
  scripts: {
    serve?: string                    // 启动脚本名
    build: string[]                   // 打包脚本名列表
    defaultBuild?: string             // 默认打包脚本名
    custom?: { name: string; command: string }[]
  }
  outputDir?: string                  // 相对路径，空则自动探测
  port?: number                       // 期望端口，用于启动前占用检测，可空
  autoOpenExplorer: boolean           // 默认 true
  autoOpenBrowser: boolean            // 默认 true
  groupId?: string
  order: number
  createdAt: number
  lastUsedAt?: number
}

interface RuntimeState {              // 仅内存，不持久化
  projectId: string
  status: 'idle' | 'installing' | 'running' | 'building' | 'success' | 'failed'
  pid?: number
  currentCommand?: string
  startedAt?: number
  exitCode?: number | null
  logs: string[]
}
```

### 6.4 持久化文件

- 位置：`%APPDATA%/Workbench/projects.json`
- 内容：项目列表、分组列表、设置项
- 写入策略：变更即写（防抖 500ms），写入前先写临时文件再重命名，避免写坏

## 7. 异常与边界处理

| 情况 | 处理方式 |
|---|---|
| 目录无 `package.json` | 拒绝添加并提示 |
| `package.json` 解析失败 | 添加时提示文件格式错误，允许以「仅管理目录」方式加入（不可执行命令） |
| 项目路径失效 | 卡片标记「路径无效」，屏蔽操作按钮，提供「重新定位」 |
| 包管理器未安装 | 执行前检测，提示具体缺失的包管理器，不执行 |
| 命令非零退出 | 状态置 `failed`，指示灯变红，错误输出在日志面板高亮 |
| 打包成功但输出目录不存在 | 回退打开项目根目录，并在日志中提示未探测到产物目录 |
| 端口被占用 | 启动前提示占用端口与 PID，提供「结束占用进程并重试」 |
| 同一操作重复触发 | 按钮置灰，忽略重复点击 |
| 应用崩溃 / 被强杀 | 启动时清理无主进程（可选：记录 PID，下次启动时校验） |
| 网络异常导致安装失败 | 状态 `failed`，日志展示原始错误信息 |

## 8. 非功能需求

| 类别 | 要求 |
|---|---|
| 性能 | 20 个项目的列表滚动流畅（≥55fps）；日志面板在单项目 5000 行内不卡顿 |
| 启动速度 | 冷启动到主界面可交互 ≤ 3 秒 |
| 内存 | 空闲状态常驻内存 ≤ 200MB |
| 可靠性 | 项目配置写入不丢数据；应用异常退出后重启能恢复列表 |
| 兼容性 | Windows 10 / 11 x64；Node 16+（取决于项目自身） |
| 可维护性 | 主进程 / 渲染进程共用 TypeScript 类型定义；核心模块（Scanner / ProcessManager）具备单元测试 |
| 安全 | 禁用 `nodeIntegration`，开启 `contextIsolation`，IPC 通道白名单校验 |
