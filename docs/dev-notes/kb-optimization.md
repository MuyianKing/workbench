## 1. 现状事实（已核对）

- 知识库是用户在别处维护的独立文件夹，布局：`kb/`（条目）、`data/raw/`（库内原始资料兼容层）、`index/index.json` 与 `kb/_catalog.md`（生成物）。
- **来源 = 一个名字 + 本机一个文件夹的映射**：`data/raw/<名称>` → 本机某个文件夹。文件夹里可以有任意多笔记、文件、子目录，应用不假设结构；来源不是笔记，也不是清洗单位；应用对来源文件夹只读，不搬运 / 复制 / 删除任何文件。
- 条目的 `source` 写**逻辑路径** `data/raw/<名称>/…`，不写本机绝对路径；本机路径只存在设置里（`kbRawSources`，每条带 `root` + `name` + `dir`，只对本机成立）。
- 跨设备：条目与生成物通过知识库文件夹自己的 Git 仓库同步（手动点同步，推整棵工作树）；来源配置不随仓库走，换设备要各配一次；映射到库外的来源资料不在知识库仓库里，不参与同步。
- 跨设备身份：应用认的是**逻辑路径**，不是内容。同名来源 + 同相对路径 = 同一份原始文件；Git 是字节一致的外部保证。
- 状态判定目前是 **mtime 启发式**：条目 `source` 与 raw 文件配对；没有条目指向 = 未入库；raw 文件比指向它的最新条目还新 = 有更新。Git checkout / pull 会重写 mtime，跨设备可能不一致。本次决定引入**内容指纹**解决（见第 4 节）。
- 当前应用对条目**只读**：唯一的写是重建 `_catalog.md` 与 `index.json`；条目的新建 / 覆盖由清洗时的 Pi 完成，应用从不删除条目。本次会新增一个受控的删除入口（见第 4 节）。
- 当前清洗 / 状态单位是**文件级**：扫描出平铺文件清单，状态按文件配对，清洗清单逐文件列。本次维持文件级（见第 5 节）。

## 2. 优化点一：移除库内 `data/raw` 兼容层

**状态：【已定】。**

动机：实际使用中不会把原始文件 copy 进知识库仓库，来源都是自己的笔记 / 项目文件夹；库内 `data/raw` 只剩“让老库还能读”的兼容作用，留着等于维护两种来源。

### 要做的

- 来源只来自外部映射：去掉 `inRepo` 这种“没配路径就读库里那份”的状态；来源行只剩 `mapped` / `unconfigured` 两种。
- 去掉 `shadowed`（“库里还留着一份”）、`origin: 'repo' | 'source'`（同名两份的区分）、`kbVisibleRawEntries`（把被映射顶掉的库里副本摘掉）。
- `kb_scan` 不再下探 `<知识库根>/data/`，遗留副本不参与扫描、不参与任何统计。
- **逻辑路径 `data/raw/<名称>/…` 保留**：条目的 `source`、正文里的相对链接、状态配对、巡检、清洗提示词都按它走；物理上的 `data/raw` 删掉，但命名空间不变，条目一个字都不用改。
- `looksLikeKb` 不再认 `data/raw`，只认 `kb/` 与已配来源。
- 同步范围变小：知识库仓库 = 条目 + 生成物；raw 不再随知识库仓库走。
- 清洗提示词简化：所有目标都必然带真实绝对路径，去掉“绝对路径以逻辑路径结尾就不重复写”的分支；“带实际文件时读绝对路径”变成无条件规则；`source` 仍写逻辑路径。
- **迁移：完全手动**。库内已有的 raw 由用户自己挪到库外一个文件夹，用**同名来源**配一条映射；条目不用改。应用不自动迁移、不移动任何文件，也不给一次性提示；遗留的 `<知识库根>/data/raw` 完全忽略。

### 要同步改的文档

- [kb.md](../modules/kb.md) 的「约束」与「实现」：删除库内 raw 兼容层、来源三种状态变两种、同步范围。
- [features-and-architecture.md](../features-and-architecture.md) 的目录结构与数据隐私相关段落。
- 知识库仓库自己的 README（仓库在应用外，需要你那边同步改）：`data/raw` 不再是物理投放区，只是逻辑命名空间。
- [kb-clean.ts](../../packages/kb/src/kb-clean.ts) 的提示词与单测。

## 3. 优化点二：来源名作为跨设备身份 + 添加时核对

**状态：【已定】。**

### 规则

- **来源名是跨设备身份键**：只要两边红框里的名字一模一样，就当成同一份来源；本机文件夹只是映射，换机器可以指到不同路径。
- 名称必须一模一样。名称相同的来源 + 来源内相对路径相同 = 同一份原始文件。
- **大小写敏感（口径 B）**：`Mu-UI` 与 `mu-ui` 是两个不同的来源。Rust 侧不再用 `eq_ignore_ascii_case` 匹配来源名；TS 侧判重、配对也按精确名字。`data/raw` 这一层前缀可以继续保持大小写不敏感（文件系统习惯），但来源名那一段必须精确。
- 来源内的文件路径（`<内层>`）仍按 Windows 口径大小写不敏感：它是文件系统路径，不是身份键。
- 名称入库前会收敛：trim、去控制字符、拒绝 `/` 与 `.` / `..`、上限 60 字符；“一模一样”指收敛后的名字。
- 名字定了不给改名（现有规则）；改名的实质是“移除 + 重新添加”，会切断条目的 `source`。

### 添加来源时的名称核对

依据不是别的设备的配置（应用看不到），而是**知识库里已有条目的 `source`**——`data/raw/<名称>/…` 是唯一能跨设备看到的名字；再加上本机已配的来源。

- 打开「添加原始数据」时，把库里条目引用过的来源名列在名称框下面（可点选）。
- 输入时实时比对：
  - **完全一致**：正向提示“库里已有条目引用这个名称”，正常添加。
  - **忽略大小写后相等、但不是精确相等**：警告“库里引用的是 `mu-ui`，你输入的是 `Mu-UI`，名称必须一模一样”，给一个“使用 `mu-ui`”的按钮。
  - **编辑距离 ≤ 2**（大小写不敏感比较）：警告“库里没有条目引用这个名称；如果是笔误，最接近的是 `…`”，用户确认后可以继续。
  - **其他**：当新来源，不提示。
- 点添加时：
  - 名称在本机已存在（精确比较）：不让重复添加，给“改它的文件夹”的入口。
  - 文件夹已经挂在别的名称下：阻止，不让同一个文件夹挂两个名字。
  - 用户确认“不是同一个来源”：允许用新名称继续添加；大小写不同的名字也算不同来源。
- 知识库还没有任何条目时，没有可参照的名字，只能和本机已有来源比；那种情况下第一次起的名字就是后面的基准。

### 实施细节

- 名称提示的文案、候选列表的交互形式在组件里定。
- “编辑距离”用简单的 Levenshtein，对库里已引用的名字逐个算；名字通常很短，成本可忽略。

## 4. 优化点三：失联条目的清理（原始资料被删后）

**状态：【已定】。**

### 背景

删除原始笔记不会删条目：条目还在、内容不变，只是 `source` 指向的文件 / 文件夹不在了。巡检会记一条“出处指不到库里的文件”，但界面不展示巡检（“算而不显”），所以现在界面上看不出异常，也没有清理入口。

### 规则

- **单位是文件级**：一个 raw 文件是失联判定的最小单位；一个 raw 文件拆出的多条条目归为一组。
- **标记放在原始数据签的来源行**：来源行显示“已删除 N”（N = 该来源下失联的 raw 文件数）。点开弹清理列表：按 raw 文件分组，每组列出指向它的条目，确认后整组删。
- **不新增“已删除”状态**：不扩展 `KbRawStatus`、不加 chip、不造虚拟 raw 行；标记是每次重扫时算出来的**派生值**，不落盘、不进状态机，条目删掉标记自然消失。
- **应用立即删除**，不交给下一轮清洗；**按组删**，不逐条拆开。
- **删除后自动重建索引**（与清洗收尾同一条路），然后刷新清单。
- **不提示入链**：确认框只列将删的条目；删完产生的断链由巡检记录（界面不展示）。
- 删除动作是应用第一次获得“删条目”的能力，做成受控例外：
  - 新增删除命令，严格校验只删 `kb/` 下的 `.md`，排除 `_catalog.md`，拒绝路径穿越；
  - 确认框列出将删的条目，提示永久删除、只有 git 提交过的才能从历史恢复；
  - 删除后条目没了，来源行上的“已删除 N”随重扫消失；来源配置本身不动（用户要移除来源仍是另一个动作）。

### 什么才算失联（安全边界）

三条同时成立才算：

1. 条目的 `source` 能解析到一个**已配置的来源**（`data/raw/<名称>/…`，带不带前缀都认）；
2. 这一轮扫描里那个来源**读成功了**（`error` 为空）；
3. 扫描清单里确实找不到这个文件。

补充：

- 来源未配置、盘不在、路径打不开时只报“来源不可用”，**绝不给删除入口**。
- **整个来源文件夹被删**：**不做任何操作、不做任何提醒**（2026-11-14 改定的口径，推翻最初
  「父目录可读即判定已删除」的方案）——「文件夹被删」与「盘不在」扫描分不清，宁可不判定；
  该来源下的条目只是出处失效（巡检记录），等来源恢复、或用户自己移除来源。
- `source` 写成书名、网址、非来源路径的条目不进清理逻辑。
- 条目没有 `source` 的不进清理逻辑。

### 指纹（替代 mtime 的跨设备误报）

- 每次扫描对**所有有条目指向的 raw 文件**算 SHA-256，不用 mtime 做前置过滤；没有条目的文件（未入库）不参与哈希比较。
- 哈希写进条目 frontmatter 的 `source_hash` 字段；清洗前由应用对清单里的每个文件算好，写进提示词，Pi 按提示词写进条目。
- 状态比较：当前文件哈希 vs 指向它的最新条目里的 `source_hash`。相同 = 已入库；不同 = 有更新；条目没有 `source_hash`（旧条目）→ 回落 mtime。
- 一个 raw 文件拆成多条条目时，它们共享同一个 `source_hash`；以最新条目的值为准。
- 代价：每次扫描会读所有“有条目指向”的文件；来源里有大文件或网络盘时会变慢。这是选择全量指纹的明确代价，不做 mtime 预过滤。

## 5. 优化点四：清洗 / 状态的最小单位

**状态：【已定】文件级（维持现状）。**

- 每个文件独立算“未入库 / 有更新 / 已入库”；清洗清单逐文件列；条目的 `source` 写具体文件。
- 来源文件夹仍然只是容器，里面可以有任意多笔记 / 文件 / 子目录；应用不假设“一篇笔记 = 一个文件夹”，也不把子文件夹当单位。
- 后果：一个笔记文件夹里有多个文件时，它们各自独立计数；图片 / 附件如果没有条目指向，就是未入库。这是文件级口径的既定取舍。

## 6. 已知限制

- **全量指纹有 I/O 成本**：每次扫描都读所有“有条目指向”的 raw 文件；大文件、网络盘会明显变慢。这是为了跨设备准确判定而接受的代价。
- **旧条目没有 `source_hash`**：在重新清洗之前继续回落 mtime，跨设备仍可能误报。
- **应用看不到另一台设备的来源配置**：添加来源时的名称提示只能基于知识库条目里的 `source`；如果某个来源还没产生任何条目，就没有参照。
- **名字即身份**：应用仍按“同名来源 + 同相对路径”认定同一份文件；指纹能发现内容不一致（变成“有更新”），但不做“是不是同一篇文档”的语义判断。
- **来源在盘符根 / 网络路径时**：与整个文件夹被删同一条处理 —— 不判定、不提醒（扫描分不清「被删」与「不可达」）。
- **清洗期间源文件被改**：应用在清洗前算的哈希可能和 Pi 实际读到的内容有微小时间差；这是极窄的竞态，不额外处理。

## 8. 验收清单

- **添加来源**：精确同名无警告；忽略大小写相同有警告并能一键改成库里的精确写法；编辑距离 ≤ 2 有警告；本机重名被阻止；同一文件夹挂两个名字被阻止；`Mu-UI` 与 `mu-ui` 能作为两个不同来源存在。
- **移除库内 raw**：`data/` 不再被扫描；来源只来自外部映射；知识库仓库同步内容不再包含 raw；旧条目 `source` 仍能解析；遗留 `data/raw` 被完全忽略。
- **指纹**：raw 内容变化 → “有更新”；只有 mtime 变化、内容相同 → “已入库”；旧条目没有 `source_hash` → 回落 mtime；未入库文件不参与哈希。
- **失联清理**：来源不可用时没有删除入口（整个来源文件夹没了时**什么都不出现**）；来源可读且文件不存在时来源行出现“已删除 N”；确认后整组删除；删除后自动重建索引；标记消失；只删 `kb/` 下的 `.md`。
- **删除风险**：不提示入链；删完产生的断链由巡检记录，不阻塞删除。
- **跨设备**：同名 + 同内层路径在两边解析到各自本地文件夹；大小写不同解析不到；内容不同时指纹判定为“有更新”。

## 9. 决策记录（原疑问，已逐项回答）

1. **清洗 / 状态单位**：文件级（维持现状）。不按笔记文件夹或整个来源算。
2. **大小写口径**：B，大小写敏感。`Mu-UI` 与 `mu-ui` 是两个来源；Rust 与 TS 的匹配、判重都要改成精确。
3. **失联标记位置**：原始数据签的来源行，显示“已删除 N”，点开按 raw 文件分组清理。
4. **删除分组单位**：文件级，按 raw 文件整组删；来源根可读且文件确实不在才出现；**整个来源文件夹被删不判定、不提醒**（2026-11-14 修订）。
5. **删除后索引**：自动重建，并刷新清单。
6. **删除前入链提示**：不提示；断链交给巡检记录。
7. **遗留库内 `data/raw`**：完全忽略，不扫描、不提示；用户手动迁移。
8. **“下次清洗带进去”**：不需要额外动作；立即删除并重建索引后，下一轮清洗看到的就是删除后的状态。
9. **跨设备 mtime 误报**：引入全量指纹（只对有条目指向的 raw 文件），SHA-256 写进条目 frontmatter 的 `source_hash`；旧条目回落 mtime。
10. **来源文件夹被删的判定**：**不做判定**（2026-11-14 修订，推翻「父目录可读即已删除」的原案）——被删与盘不可达分不清，整个来源没了就当无事发生；失联清理只认「来源读成功、且具体文件不在」。
11. **名称“接近”的判定**：完全一致；忽略大小写相等（警告）；编辑距离 ≤ 2（警告）；其他当新来源。
12. **库内已有 raw 的迁移**：手动挪出并配同名来源；应用不做自动迁移、不移动任何文件。
13. **来源行的删除入口**（2026-11-14 补充）：右键菜单两项 ——「删除」只删配置（可逆，不弹确认）；
    「删除并清除条目」删配置并清掉名下全部条目（不管 raw 文件在不在，确认框列出将删的条目，
    删条目 → 删配置 → 重建索引 → 刷新）。来源文件夹里的文件一律不动。

## 10. 实施细节（不阻塞方向）

- `source_hash` 的字段格式（纯 hex 还是带 `sha256:` 前缀）、提示词里的写法。
- 指纹命令的入参形状（传 rel 列表还是整份清单）、失败时把该文件按“无法判定”处理并回落 mtime。
