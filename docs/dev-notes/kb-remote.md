# 知识库远程仓库化（raw/ + data/ 两层）的决策记录

> 状态：**已实施**（2026-11-14）。
> 本次需求把知识库从「条目在仓库、原始资料在库外来源文件夹」翻成「**仓库里物理分两层** ——
> `raw/` 原始数据、`data/` 清洗数据」，列表数据来自远程仓库，清洗前必须把原始文件上传远程。
> 相关实现见 [kb.md](../modules/kb.md)、[kb.ts](../../packages/kb/src/kb.ts)、
> [kb.rs](../../apps/desktop/src-tauri/src/kb.rs)、[stores/kb.ts](../../apps/desktop/src/renderer/src/stores/kb.ts)。
> 上一轮优化的记录见 [kb-optimization.md](kb-optimization.md)（其中「库外来源映射」「应用不搬运
> 任何文件」等口径已被本次推翻，见第 10 节）。

## 1. 需求原文与解读

- 远程仓库结构：`raw` 存原始数据，`data` 存现在的清洗数据。
- 界面：去掉顶部 tab；没有什么原始数据，只有知识库；「添加原始数据」改为「添加知识库」，
  第一次添加直接清洗（需要二次确认，不清洗就当做不添加知识库）；只有一个知识库列表，
  列表数据来自远程仓库 —— 在存放原始数据的那一层增加一个配置文件，可以直接解析存放
  原始数据的那个目录结构；列表的子文件如果没有关联本地文件直接用远程仓库的；列表右击
  可以删除知识库（需要删除关联的清洗数据）、清洗知识库（有更新）；列表的子文件关联了
  本地仓库可以删除文件（需要删除关联的清洗数据）、清洗文件（有更新）；所有的清洗操作
  之前必须将原始文件上传远程仓库。

## 2. 与用户确认过的四个定案

1. **条目不做预览**：用户只关心源文件。条目清单仍在 store 里读（状态判定与失联清理绕不开
   frontmatter），但不上界面 —— 条目树、条目阅读、标签分布、巡检（kb-lint.ts）一起退役。
2. **打开页面自动 pull**：列表数据来自远程仓库，进页面后台 `kb_pull` 一次（只拉不推，
   `--autostash` 保护未提交现场）；冲突不挑边、失败只把原因摆到同步那行，不变成一页错误。
   这是同一条 kb 仓库出口、触发时机多了一处（features-and-architecture.md「数据与隐私」
   已同步改写）。
3. **应用做一次性迁移**：`kb/` → `data/`、来源复制进 `raw/<名>/`、`data/raw/` 前缀改写、
   写清单、删旧 index/，确认弹层列明四步后一次做完；只能迁移一次（清单已存在时 Rust 拒绝）。
4. **模型确认**：一个知识库 = `raw/` 下一个子目录；添加时选一个本机文件夹作为**持续关联**
   的源头并复制上传；之后本机改文件夹 → 复制进 raw → 上传 → 清洗写 `data/<名>/`；
   没有关联的设备只读仓库里的 raw 副本。

## 3. 仓库结构与清单

```
<kbDir>/                  用户 clone 的 git 仓库（应用不 init、不 clone、不改 origin）
  raw/                    原始数据层（物理目录，进同步）
    kb.json               清单：{version:1, kbs:[{name, created}]}，列表数据源，应用维护
    <知识库名>/…           一个知识库的原始文件（保留子目录结构）
  data/                   清洗数据层（条目 + 生成物）
    <知识库名>/…           该库条目（内层 NN-主题/，由清洗提示词约束）
    index.json / _catalog.md   生成物（原 index/index.json 与 kb/_catalog.md 挪入）
```

- 清单是列表的唯一事实源：`parseKbManifest`（认不出回 null 不是错误）、
  `serializeKbManifest`（应用写：sanitize + 去重）。清单没有的知识库不占行、raw 里有
  文件但清单没登记的也摆不出来。
- 知识库名 = 目录名，跨设备身份键、精确比较（大小写敏感）；sanitize 挡分隔符与 `.` / `..`。
- 旧前缀 `data/raw/`（老结构的库内物理副本）没有任何身份：不算条目、不算原始数据、
  应用不改不删，迁移也不碰它。

## 4. 出网与 git

- `sync.rs` 抽出 `sync_folder` 共用实现（笔记 / 知识库同一套流程：锁、busy、凭据、fetch、
  commit、pull --rebase --autostash、push，冲突不挑边），两个薄壳：
  `kb_sync`（提交信息 `kb: <设备名>`）与 `kb_pull`（只拉不推）。`commit_notes` 加了前缀参数。
- 出网点清单（「数据与隐私」一节已改写）：同步按钮（用户点）、**打开页面后台 pull**、
  **清洗前后各一次 kb_sync**（前置上传 + 推条目）。地址与内容不变：都是知识库仓库自己的 origin。
- 应用仍不 init、不 clone、不改 origin；没仓库 / 没远端时同步与清洗都如实拦。

## 5. 添加知识库（首洗一体）

弹层两页：表单（名称 + 源头文件夹；名称按清单核对，同名拦住）→ 确认页（三步说明，
「现在取消的话这个知识库不会被添加」）。确认后 store 的 `addLibrary` 做完**本地几步**
（源头复制 `kb_source_sync` 全量 → 写清单 → 存关联，不到一秒）就关弹窗，随后
`startClean({kind:'kb'})` 接管 —— 上传是清洗的硬前置，在清洗的准备阶段做（面板逐步
可见，失败就地拦下；本地已添加的保留，重试「同步」补上后可再洗）。
「不清洗就当做不添加」由**拦路前置**保证：重名、文件夹冲突、清洗环境缺、没连远端都在
复制之前拦。弹层不替上传转圈 —— 那几秒交给清洗面板的日志。（2026-11-14 修订：
原先上传在弹层里做，列表先出现而弹窗空转几秒，体感是「点了没反应」。）

## 6. 清洗（上传硬前置）

`startClean(scope)` 五步：① 范围内有关联的知识库做源头同步（只增改不删）；② 有复制就
reload（状态清单以同步后的 raw 为准）；③ `kb_sync` 上传 —— 没连远端 / 失败一律拦下
（进清洗面板 blocked 态）；④ 算清单（未入库 + 有更新，按范围过滤；空了就明说「没有要
清洗的」）；⑤ 专用 Pi 会话。收尾（`finishClean`）：重建索引 → `kb_sync` 推条目（失败不
算失败，面板里留一句「点同步补一次」）→ reload。

提示词改写要点：目标 `data/<名>/…`（与原始文件同名目录）、`source` 写 `raw/<名>/…`、
禁令「raw 层一个字不许改、上传与 git 归应用」、生成物 `data/_catalog.md` 与
`data/index.json` 不碰。`splitCleanWrites` 只认 `data/` 下的 `.md`（排除 `_catalog.md`
与遗留 `data/raw/`）。

## 7. 状态判定与已知取舍

- 口径维持「指纹优先、mtime 回落」，只是配对前缀从 `data/raw/` 换成 `raw/`（简写不带
  前缀仍认）。**有关联的知识库以本地为准**（2026-11-14 测试反馈后修订）：`kb_scan` 带
  「知识库名 → 本机源头文件夹」关联（Rust `walk_local` 顺路算源头逐文件 SHA-256），
  本地这份存在就以本地指纹 vs 条目 `source_hash` 判（`matchKbRawStatus` 的 `localFiles`
  参数）；本地没有这份（没关联 / 本地删了 / 没算出）回落仓库副本。首次实现只有仓库视角
  （源头改动要等清洗才可见），测试中判「本机 b.md 改了不亮」不符合直觉，改为本地为准。
- 已知取舍（写进 kb.md）：新增的本地文件要等清洗前的源头同步把它带进 raw 才显示
  （状态以 raw 行为载体）；直接在源头里删文件也不会自动同步进 raw（列表里删文件才会
  两边一起删）。
- 失联判定简化成两条（source 解析到清单里已有的知识库名 + 扫描清单里找不到文件）：
  raw 在仓库里，没有「盘不在与被删分不清」的情形了。

## 8. 删除

- 删知识库（右键，始终可用）：条目（全部）→ `kb_delete_tree`（raw/<名>/ + data/<名>/）→
  清单移除 → 关联移除 → 重建索引 → 上传；源头文件夹一个字不动（确认框写明）。
- 删文件（右键，仅有关联时）：`kb_file_delete` 仓库 + 源头两边一起删（源头持续关联着，
  只删仓库那份会在下一次源头同步时回来）→ 指向它的条目一并删 → 重建索引 → 上传。
- 失联清理沿用旧编排（确认 → 删条目 → 重建索引 → 上传 → 刷新）。

## 9. 迁移（一次性）

触发：`kb/` 在、清单没有 → 工具条出「迁移」。确认弹层列四步 → `kb_migrate`（Rust）：
① 各来源文件夹复制进 `raw/<名>/`（跳过噪音、已存在不动、与仓库重叠拒）② `kb/` 整体搬进
`data/`（撞名如实失败）③ `data/` 下所有 `.md` 的 `data/raw/` 前缀改写为 `raw/`
（frontmatter source 与正文相对链接同一段写法，一并改对）④ 删旧 `index/` → 写清单
（从本机关联造）→ 重建索引 → 上传。只能做一次。

## 10. 被本次推翻的旧口径（相对 kb-optimization.md）

- 「来源 = 库外文件夹的映射、应用不搬运 / 复制 / 删除任何文件」→ raw 层物理进仓库，
  应用复制（源头 → raw）、删除（删知识库 / 删文件会删到源头文件夹里的文件）。
- 「同步只推条目 + 生成物，来源资料不进同步」→ 整棵工作树（raw + data）都进同步。
- 「来源名靠条目 source 核对」→ 清单（raw/kb.json）是名称核对的参照（条目也仍有参照
  价值，但清单是唯一权威）。
- 「来源行有 `unconfigured` / `error` 状态」→ 关联只有「有 / 没有」两态；raw 在仓库里
  读不到的情形只剩仓库本身坏了（整页报错）。
- 「条目树 / 条目阅读 / 标签分布 / 巡检」→ 全部退役（用户只关心源文件）。
- 「打开页面不出网」→ 打开页面后台 pull 一次（用户已拍板）。

## 11. 界面只说原始文件的事（2026-11-14 追加，测试反馈）

原则：**清洗的数据用户看不懂、也不关心** —— 界面上只出现原始文件（本机源头的或远程
仓库副本的）。据此清掉的漏出点：原始查看的「N 个条目整理自它」、概览的条目数与索引区、
清洗收据里的 `data/…` 条目路径（store 按写入条目的 source 映射回 raw 层，收据分
「新入库 / 重新入库」两组原始文件）、三个删除确认框里的条目路径清单（只给数量）、
工具条的「重建索引」按钮（应用在每个写点自动重建，手动入口没有存在意义）。
状态词（未入库 / 有更新 / 已入库）保留 —— 它是「要不要清洗」的行动信号，不是产物展示。

**有关联的知识库，本机是事实源**（同日追加，测试反馈「查看的不是最新内容、路径显示
raw/… 没有意义」）：`kb_read` 带关联清单，raw 层的文件本机源头里有就读本机的
（最新内容），没有才读仓库副本；`matchKbRawStatus` 的本地覆盖同时把 `abs` / `mtimeMs`
落在本机那份上 —— 查看器的路径、修改时间、「用系统默认程序打开」、清洗清单给 Pi 的
地址全部指向本机文件。没关联的知识库从头到尾就是仓库副本（路径显示仓库内的 `raw/…`）。

## 12. 仓库里的 AGENTS.md（2026-11-14 追加，让外部 AI 认得这个仓库）

知识库是给 AI 用的，但任何外部 AI 工具进仓库都不知道这是什么。解法：**仓库根放一份
应用生成的 `AGENTS.md`**（内容是应用的口径：两层结构、清单与生成物禁改、条目格式、
「先检索 data/ 再读 raw/」「改内容去 raw 重新清洗」），Claude Code / Codex 这些自动读
AGENTS.md 的工具进仓库即得。要点：

- **已存在时不覆盖**（用户可能补了自己的说明）；调用点：添加知识库与迁移之后
  （Rust `kb_agents_doc` / `agents_doc_write`，内容常量在 kb.rs）。
- 清洗提示词的「仓库根下的其他文件不要碰」盖住它 —— 只归应用写。
- 应用内 AI 助手页**不做注入**（用户选了只做仓库文件这条路；外部工具与本应用都
  各有各的入口）。

## 13. 验收清单（手测）

- 添加：名称与清单核对（同名拦 / 大小写提醒 / 笔误提醒）；二次确认不确认就不添加；
  确认后 raw/ 出现目录、清单更新、远程有提交、清洗面板自动开跑。
- 清洗前置：没连远端时清洗被拦（面板说明原因）；源头改文件后清洗，改动先进 raw 再上传
  再洗；无待洗时明说「没有要清洗的」。
- 删除：删知识库后 raw/ 与 data/ 两层消失、清单少一条、条目清空、远程有删除提交、
  源头文件夹原样；删文件两边一起删、条目一并删。
- 失联：别的设备删了文件，本机 pull 后知识库行出现「已删除 N」，清理后条目消失。
- 迁移：旧仓库进页面出「迁移」按钮，确认后 kb/ 搬 data/、来源进 raw/、source 前缀改写、
  状态判定（已入库）不因迁移误报；再点迁移被拒。
- 自动 pull：另一台设备推的变更，本机重新打开知识库页后列表即出现。
