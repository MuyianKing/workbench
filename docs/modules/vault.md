### 密码学与密钥

- **加解密一律在渲染层，用 WebView2 自带的 WebCrypto**（`packages/vault/src/vault.ts`）。Rust 侧**一行密码学都没有**，
  也不要为了「挪回后端」去引 `rsa` / `p256` / `aes-gcm` 这类 crate —— 它们都会拉进成片的编译单元
  （AGENTS.md 第 1 节的「不新增编译单元」）。
- **本机密钥过一次 IPC，这是全项目唯一的例外**（`vault_key_read` / `vault_key_write`）：解密后的正文本来就要在
  渲染层显示，而 Rust 侧没有能做这件事的工具。**别推广这个例外**：账号 access_token 仍只在 Rust 侧流转
  （给 git 用），不进渲染层。
- 密钥是**一把 ECDH P-256 密钥对**，私钥在 Windows 凭据管理器（`Workbench/vault/key`，DPAPI 按当前用户加密），
  **不进数据文件、不进仓库**。公钥写在文件里（`key` 字段）—— 公开信息，作用只有一个：让「这份文件是用别的密钥
  加的密」当场看得出来。
- 每条条目走一次 **ECIES**：现生成临时密钥对 → 与公钥 ECDH → HKDF-SHA256（盐与 info 都是常量）→ AES-256-GCM。
  **别把 HKDF 那两步换成「用公钥直接加密」**：ECDH 只是密钥协商，少了 KDF 等于把共享秘密当密钥用。
  临时密钥对**每次现生成**，同一条正文加密两次密文完全不同。
- `seal` 收公钥，而 `VaultPrivateKey` 在结构上是 `VaultPublicKey` 的子集 —— **收公钥的地方一律先过 `publicKeyOf()`**，
  不能把入参整个交给 `importKey`：带 `d` 的 JWK 会被当成私钥，报出一句与「密钥不对」无关的
  `Usages cannot be empty`。
- **界面不摆「主口令」这一层，也不要加**：密钥存在本机（用户的要求），「坐在机器前」这层确认交给 Windows。
  加本地口令只会多一个能忘的东西，挡不住已经在这台机器前的人，而忘掉口令就是条目全丢。
- **解锁那道闸由 Windows 认**（vault.rs 的 hello / 本机账户密码两节），应用不存凭据、不存哈希、不派生：
  - **默认走 Windows Hello**（`UserConsentVerifier`，弹系统验证框，PIN / 指纹 / 人脸），验的是登录界面实际用的
    那个凭据，微软账户与本地账户都成立。它已在编译图里（tao 引的 `windows` 0.62 + `windows-future` 0.3，
    只开 feature / 复用，不新增编译单元）；等验证收场用 `join()`，用户关掉不算失败。**必须走带 HWND 的
    `IUserConsentVerifierInterop::RequestVerificationForWindowAsync`**：不带窗口的 `RequestVerificationAsync`
    弹出的框会被压在主窗口后面，用户只当没弹（微软 tracker 已知问题，实测如此）。
  - **没配 Hello 才退回输本机账户密码**（`LogonUserW` + `LOGON32_LOGON_NETWORK`）。**这条路只验本机 SAM**：
    微软账户的密码由云端认，SAM 那份内部副本对不上 —— 那类机器上输什么都没用，连每天登录的正确密码也过不去
    （2026-10 在开发机上实测坐实）。所以它只能是回退；渲染层凭 `vault_hello_state` 分流，`unconfigured` 的机器
    界面上要说一句去哪儿配 PIN。
  - 一次密码校验失败就是一次真实登录失败（计入系统锁定计数），别把那条命令当「试密码」的地方。
- **「收起密码」不是加密也不是注销**，只是把明文从屏幕与内存撤掉；真正的闸是上面那道 Windows 验证 —— 挡得住
  不知道这台机器凭据的人，挡不住知道的人（包括用户自己）。一个叫「锁定」的按钮会让人以为它挡得住别人，
  所以它叫「收起」。
- **换 / 导入密钥之后必须走一遍 `adoptKey`**（`workbench/vault.ts`）：能读出来的条目解开再用新密钥封回去，
  读不出来的留墓碑。「能读出来」要拿两把都试 —— 上一把在手上就按它解，不在手上（新机器没解锁就导入、重启后
  导入）也要把刚换上的那把试一遍；漏了这步，锁着导入一次就把整份保险库误杀成墓碑（2026-09-30 事故）。
  少了 `adoptKey`，旧条目会以「只在远端有」的身份在下一次同步被并回本机 —— 合并只认 id 与时间、看不见密文，
  界面上就多出一堆永远解不开也删不掉的条目。换密钥的代价要跟用户说全：别的机器得重新导入新密钥。

### 文件与合并

- 文件形状见 `packages/vault/src/vault.ts` 的 `VaultFile` / `VaultItem`。**信封明文、正文密文**不是疏漏：
  跨设备合并在没有密钥时也要算出同一个结果 —— 认身份靠 `id`、判新旧靠 `updatedAt`、破平靠 `by`、认删除靠
  `deleted`。**给信封加字段要同时想清楚它在合并里是什么意思**，否则两台机器各执一词。
- `mergeVaultItems` 是**同步的全部**，两条不能破：
  1. **必须纯、且两边算出的结果逐字节一致**（`updatedAt` 大的赢、撞上时 `by` 大的赢、输出按 id 排）。
     任何一处「以本机为准」都会让两台机器来回覆盖、永远收敛不了 —— 那里有单测钉着，改口径先改测试；
  2. **墓碑永不清理**。清掉之后，一台离线很久的机器回来时本地那条老记录就成了「只在一边出现」的并集项、
     被原样推回去 —— 用户看到删掉的密码自己回来了。墓碑约 90 字节，留着不心疼。
- **恢复被墓碑盖掉的条目时 `updatedAt` 必须一起换新**：合并只按时间判新旧，把历史密文重封、时间戳照抄原文，
  下次同步就被原来那块墓碑赢回去（2026-10-16 真发生过）。墓碑本身一个字都别动。
- **改动只重封那一条**（`workbench/vault.ts` 的 `save`）：整份重加密会让字节全变，「内容没变就不产生提交」
  随即失效，仓库堆一串无意义提交。
- 条目的 `id` **落盘之前就得存在**（新建时现生成 uuid）：它是跨设备合并唯一认得出「同一条」的东西，
  保存时才现编的话两台机器各存一份就成了两条。

### 这一页的对齐口径

界面**靠量不靠看**（`getBoundingClientRect` + `getComputedStyle`，配方见
[dev-notes/browser-preview-verification.md](../dev-notes/browser-preview-verification.md)）—— 这一块前后错过四次
（工具带比卡片墙右 10px、卡片行三条中线、段头小字矮两像素、引导屏比导航栏低 10px），每次都是「看着不对但说不出
哪儿」：

- **一条左基准线**：工具带、段头、卡片左缘都在 `left: 108`。工具带那份留白归外壳（global.css 的
  `.vault > .filter`，取 `--card-gap`），段头不留内边距 —— 两处都写就是两倍。**段头那个收起 / 摊开的小箭头
  排在条数后面**：摆标题前面会把标题顶右十几像素、与卡片左缘错开。
- **一条顶线**：导航栏卡片、工具带、引导屏面板的 `top` 都是 0（紧贴顶栏下沿）。
- **卡片那行是 22px 一条带子**：标签、值、图标三者同高同顶。
- **字号不同的文字按基线对齐**，不按盒子居中。
- 引导屏里**文字与按钮等宽同左缘**，图标居中；宽度按 `--fs-meta` 折算（写成 `32em` 会跟各自字号走，
  按钮排继承 `.empty` 的 `--fs-title`，两个 32em 差 96px、左缘差 48px）。

### 同步

- 文件在同步仓库的 `vault/vault.json`（`paths.rs` 的 `VAULT_DIR` / `VAULT_FILE`），与用量 / 外观 / 图片 / 笔记
  **同一个仓库、同一条凭据**，**不是第七个网络出口**：没登录就没有同步（适配层经 `syncRepo()` 取地址），
  保险库没登录照常能用，只是推不出去。
- **同步是自动的**：进这一页一次（`VaultView` 的 `onActivated`；冷启动时这页还锁着，那一趟由解锁补上）、
  每次增删改之后各一次 —— **工具带上没有同步按钮**。**同一时刻只跑一轮**：跑着时又动了一条，等这轮收场补一趟
  （`stores/vault.ts` 的 `inFlight` / `queuedAgain`）；两轮并行会各拿同一基准去写，后一轮被 `vault_push` 挡回，
  白跑还多一次往返。**失败只在工具带留一行字**（`syncNote` / `syncFailed`），不弹消息 —— 进一次页面弹一次
  「同步失败」比不说还烦；重试就是再进一次这页、或再动一条。成功一个字都不写。
- **拉和推整段拿在 `token-sync` 那把锁里**（`vault.rs` 的 `pull_at` / `push_at` 开头 `sync::lock_workflow`）：
  用量 / 外观 / 网关三条也落在这个克隆上，并发时 git 会互相踩（`index.lock`、`Cannot fast-forward`）。
  另一个窗口（安装版 + dev）不在同一把锁里，由 `pull_with_race_retry` 重拉兜住；口径见
  [sync-and-auth.md](sync-and-auth.md) 的「同一个克隆上的并发」。
- **换 / 建 / 导入密钥不自动推**（只有「本机原来没有密钥」的新机器场景才顺手拉一次，见 `syncAfterKeyChange`）：
  `adoptKey` 会把两把都读不出来的条目留成墓碑，自动推等于把那台机器上还好的条目删给所有机器 —— 09-30 全量墓碑
  事故就是这么铺开的。
- **它是仓库里唯一一个多写者文件**：`token-usage/` 与 `config/` 那套「一台机器一个文件、一个写者」在这里不成立，
  所以**绝不能让 git 合它** —— 同一文件的两种改法交给 git 只会留冲突标记，而这份数据本就有确定的合并结果。
  做法是 `vault_push` 写入前核对远端还是不是合并时的基准（`base`），变过就**一个字都不写**、把远端交回去
  （`pushed: false`），渲染层重走一轮（最多三轮，见 `SYNC_ROUNDS`）。
- **推送失败不做 rebase，而是 `git reset --mixed origin/<branch>`**：把刚落下的提交退回未提交状态，免得它成为
  下一次 `ensure_clone` 里 `pull --rebase` 的源头 —— 那会卡在同一文件上每次同步都撞冲突，克隆就废了。
  这里用 `reset --mixed`（不是 `--hard`）是安全的：那个克隆是应用自己的缓存（见 `paths.rs`），每个文件都由本机
  数据现算，没有任何只存在于那里面的东西。同理 `drop_stale_rebase` 会中止克隆里遗留的 rebase。
- **本机先落盘、再推**：推送失败时合并结果也已在本机，下次同步不必从头来。
- 从远端读的是 **`origin/<分支>` 那个 ref**（`git show`），不是工作区那份：工作区可能压着上次没推的提交，
  照它读会让「远端变了没有」判断错。路径不存在靠 `git cat-file -e` 先问存在性，**不能**把 git 那句
  `does not exist in 'origin/main'` 当成失败报给用户。
- 远端那份与本机密钥对不上时**必须如实说出来**（`keyMismatch`）：那些条目能合并、能推，但这台机器永远解不开 ——
  不说的话用户看到的是「同步成功，一条都没多出来」。

## 实现

- 导航栏第六项「密码」：**按分组分段的卡片墙**（每段一个段头：分组名 + 条数；1440 窗口一行五张、每张 256px）。
  **段头不画拉到右缘的细线**（一组一张卡时那条线露馅）。**工具带上只有搜索 + 一颗「分组设置」按钮** ——
  分组筛选标签与段头把数摆了两遍，删掉：找某一条用搜索、看某一组用分段、换先后与藏哪几组去那颗按钮。
  搜索框按 `.sort` 规范（28px、`--r-sm`、`--bg-surface`），那颗按钮与密钥 / 收起几颗排一行（图标按钮 +
  `el-tooltip`）；同步那颗**撤掉了**（改成自动，见「同步」一节），那一带只在没成功时留一行字。
  **整页一条左基准线**：搜索框、段头、卡片左缘落同一条竖线（工具带左边是有硬边的输入框，差 10px 明摆着没对齐）
  —— 工具带留白由外壳给（`--card-gap`，见 global.css 的 `.filter`），段头不留内边距。
  **段头点一下收起 / 摊开那一组**（它是一颗按钮，外观推掉、宽度取 `fit-content` —— 整行可点会让悬停面拉到右缘，
  又成那道「线」）。收起时**条数照常显示**（那正是「这段里还有几条」的答案，搜索筛过之后尤其如此）。收起态
  **只活在这一页里**（组件内一个 Set，与 AI 助手页左栏那棵树同一做法）：换页不丢（KeepAlive），重启全展开 ——
  顺序与隐藏是行为记忆、要落盘，收起态是「这一眼怎么看」、不落盘。**引导屏（还没建库 / 已收起）**：段落与按钮排
  同取 `calc(var(--fs-meta) * 32)` 的宽度并左对齐，图标居中。
- 一条记录就是**名字、密码、备注、分组**四样（`VaultEntry`）—— 是**备忘不是密码管理器**：没有用户名 / 网址字段、
  不生成口令。分段用 `groupVaultRecords`（吃**排好序的那份**，相邻同组自然连段；排序管先后、分段管断开）。
  **分组名不写在卡片上**（段头说了）。卡片上只有**一行「标签 + 值」**（`密码` 灰字标签锚住值列）；**备注不上
  卡片**（长短不定，摊上去高矮不齐），跟弹框走。密码默认遮住（**固定八度**的点，不按真实长度 —— 长度也是信息）；
  **一键复制 / 一键查看**常显、压暗一档；亮着时**换行不截断**。改删收在悬停才显形的「⋯」菜单（Teleport 到 body，
  指针进菜单卡片就不算悬停，开着的要单独记 —— `openMenu`）。添加与编辑走弹框，名字唯一必填，校验就地显示
  （`vaultEntryProblem` 唯一一份规则，store 再兜一次）。
- **非对称加密**：一把 **ECDH P-256** 密钥对，每条条目单独一次 ECIES ——「有公钥能写、没有私钥读不出来」成立，
  同一条正文加密两次密文不同。形状与边界见「密码学与密钥」。
- **密钥全在本地**：私钥存 Windows 凭据管理器（`Workbench/vault/key`），**不进数据文件、不进仓库**，所以
  **没有主口令这一层**。解锁由 Windows 认（默认 Hello，没配才输本机账户密码）。**「收起密码」不是加密也不是注销**：
  它把明文从屏幕与内存清掉（离开座位按一下），解锁要过 Windows 验证 —— 但挡不住知道这台机器凭据的人。
  换机器用同一保险库 = 密钥屏**导出成文件**带过去导入一次（纯文本文件等于保险库本身，只走文件、不上屏不进剪贴板）。
- **多机同步规则**见「文件与合并」与「同步」。**同步自动**（进页一次、每次增删改后一次，无同步按钮）；
  没登录 / 没填地址就安静跳过。
- **2026-09-30 全量墓碑事故**：一台机器没解锁就导入密钥（`previous` 为 null），`adoptKey` 当时只拿「上一把」解密、
  没试刚导入的那把，把本机 11 条（含同步拉下来、明明解得开的）全留成墓碑推上去，同步又按「墓碑不复活」铺到所有
  机器。密文本体还在这台机器的 git 历史里（同步仓库 `vault/vault.json` 的旧提交），凭据管理器里的密钥没换过，
  解出来重封、打上新时间戳盖过墓碑再同步即恢复。法证特征：全部墓碑同一毫秒 `updatedAt`、同一 `by`、文件级 `key`
  换成刚导入那把 —— 手动逐条删除的时间戳各不相同。
- **2026-10-16 复发：补回来的条目被同步吃了**。09-30 之后本机手工补回过条目（时间戳沿用原文），10-16 13:32 按了
  一次同步 —— 合并按时间判，那些条目输给 09-30 的旧墓碑，本机又只剩两条邮箱。补回痕迹：13:32:19 / :24 / :31
  本机对 `08715f61` / `523d2e55` / `cf160ba6` 写下三条新墓碑（那三条当时是活的），13:32:37 推上去。
  **「墓碑是本机写的」不等于「密钥出过事」**：写墓碑只有界面删除与 `adoptKey` 两条路，而凭据管理器里密钥的最后
  写入时间还是 09-20 15:04（`CredReadW` 取回的 `LastWritten`），没换过 —— 那三条是手删；`adoptKey` 的痕迹则是
  「同一毫秒一片墓碑 + 密钥写入时间就是那一会儿」。恢复同上，只是**这次必须打上新时间戳**；另有 `b3410e09`
  是另一种密钥加的密（那台机器自带的 `key` 与其余不同），这台机器永远解不开，只能留在墓碑里。
- 界面上**如实说三件读不出来的事**：几条**解不开**（别的密钥加密的）、几条**读不出来**（内容坏了或来自更新版本）、
  **仓库那份与本机密钥对不上**（能合并能推，但这台机器永远解不开）—— 不说「同步成功，一条都没多出来」就说不通。
  密钥屏显示**公钥指纹**（`A1B2-C3D4-E5F6`），两台机器应当同串，对不上就重新导出密钥。
- **分组名收敛时 trim**（`sanitizeVaultEntry`）：排序 / 筛选 / 分段三处都按 `record.group` 一个值比，收敛只在这一处；
  适配层 `save` 回来的记录用**收敛之后**的正文（`seal` 内部也 sanitize，否则界面与磁盘差一个空白，刷新一次标签
  就换写法）。
- **分组是一栏自由文本**（`el-select` + `filterable` + `allow-create`），没有「新建 / 改名 / 删除分组」那一套、也没有
  分组表 —— 候选项从卡片现算（`groupVaultRecords` / `vaultGroups`），某组最后一条挪走那一段自己就没了；未分组自成
  一段垫底。**当前看哪一组刻意不落盘**（临时的镜片）。
- **段的先后与「哪几组不上墙」都在「分组设置」弹框里改**（工具带那颗齿轮，`VaultGroupDialog.vue`）：一行一个分组，
  **按住一行拖动换先后**、右边**开关**决定上不上墙。收进弹框的理由：分组是一份要管理的清单，而卡片墙是「用」的
  地方 —— 每段头挂两颗只在悬停显形的东西，墙上反而看不清有哪些组；两件事也都是偶尔做一次。弹框形状与「设置 ·
  菜单」的清单一致（行 + 开关 + 按住拖动），拖动同一套做法（`startPointerDrag` + 槽位算落点 + TransitionGroup 的
  FLIP 跟手重排，body 类名 `is-sorting-groups`）。**开关立刻生效**、拖动是「跟手重排、收手落盘」（`setGroupOrder`
  收整份名单）。
- **顺序与「藏起来的那几组」是行为记忆，住本机数据文件**（`vaultGroupOrder` / `vaultHiddenGroups`，收敛在
  `sanitizeVaultGroupNames`）：与 `projectSort` 同一批 —— 不进 theme.json（那会整份同步），**也不进 vault.json**
  （那份只装条目；往信封加视图偏好会牵动跨设备合并口径）。代价：换台机器要重新拖、重新藏一遍。
- **弹框里那行行 = 全部有名字的分组**（`orderedVaultGroups`）：名单里没有的排在名单之后、按名字（新加分组不必先拖
  才看得见）；**藏起来的分组照常在清单里**（开关是关的）—— 于是落盘名单一直完整，藏一下再放出来位次还是原来那个。
  **未分组不在清单里**（它不是一个组，永远垫底），段头也没有拖拽与隐藏那一套。
- **藏起来 = 整段不画、也不进搜索**（`withoutHiddenGroups` 在搜索过滤之后摘一次）：想找就去弹框开开关；一段都不剩时
  空态会明说「分组都隐藏了」并给一颗「全部显示」，免得整页空着被读成「记录没了」。**未分组藏不了**（弹框不列、
  `hideGroup` 也挡一道）：藏掉它，新加一条没归类的记录等于凭空消失。
- 布局三条硬数：**卡片行高由 22px 一个数说了算**（图标按钮压到 22px、横向内边距 4px、行高 22px —— 混进 20px / 28px
  就是三条中线，改一个要一起改）；**「⋯」平时透明但占位**（28px，悬停显形时整行不跳，别改 `display: none`）；
  同行字号不同的文字**按基线对齐**（段头 15px 名字配 10.5px 条数与那个小箭头，盒子居中会矮两三像素）。
  **引导屏上边距必须是 0**（别页第一个元素都贴顶栏下沿，再补 `--card-gap` 就低一截），左右与下仍取 `--card-gap`；
  文字与按钮共用一条左缘（同取 `calc(var(--fs-meta) * 32)`），图标居中。
