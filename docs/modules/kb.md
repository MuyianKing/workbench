# 知识库（kb）

## 约束

关键落点：`packages/kb/src/kb.ts`（布局常量、清单解析、frontmatter 解析、状态判定、本机日期，带单测）、
`packages/kb/src/kb-clean.ts`（**清洗提示词**：应用内的资产，不对外提供、开发期迭代，带单测）、
`apps/desktop/src-tauri/src/kb.rs`（扫描、读文本、**受控写动作**：源头同步 / 删知识库 / 删文件 / 写清单 / 迁移 / 重建索引 / 删条目）、
`apps/desktop/src/renderer/src/workbench/kb.ts`（适配）、
`apps/desktop/src/renderer/src/stores/kb.ts`（编排 + 清洗的全程驱动）。AI 那条驱动链路见 [ai.md](ai.md)。
跨模块通用事实见 [features-and-architecture.md](../features-and-architecture.md)，红线见 [AGENTS.md](../../AGENTS.md)。
本次改造的决策记录见 [kb-remote.md](../dev-notes/kb-remote.md)；上一轮优化的记录见
[kb-optimization.md](../dev-notes/kb-optimization.md)（其「库外来源」的口径已被本次推翻）。

- **仓库物理分两层，清单管列表**：`raw/`（原始数据）与 `data/`（清洗后的条目 +
  `data/_catalog.md`、`data/index.json` 两个生成物）都是仓库里的**物理目录**、进同步；
  知识库清单住 `raw/kb.json`（`{version, kbs:[{name, created}]}`）—— **列表数据来自远程
  仓库**：pull 下来解析它就得到列表；它**不属于任何知识库**，不算原始数据
  （`kbRawFiles` 明确排除它，否则就是一条永远「未入库」的幽灵行）。一个「知识库」= `raw/` 下一个子目录，名字即目录名
  （条目 frontmatter 的 `source` 引用它，定了不给改名）。布局常量集中在 kb.ts
  （`KB_RAW_DIR='raw'`、`KB_DATA_DIR='data'`、`KB_MANIFEST_REL='raw/kb.json'`、
  `KB_INDEX_REL='data/index.json'`），与仓库自己的 README 是一套说法。
- **仓库根的 `AGENTS.md` 由应用生成**（给任何会进仓库的 AI —— Claude Code、Codex 这些
  自动读 AGENTS.md 的工具 —— 描述「这是什么、结构长什么样、怎么用」）：内容是应用的
  口径（raw / data 两层、清单与生成物禁改、条目格式、检索指引），**已存在时不覆盖**
  （用户可能补了自己的说明）。调用点：添加知识库与迁移之后各一次（那时清单刚落盘，
  首次同步就会把它带上去）。清洗提示词的「仓库根下的其他文件不要碰」同样盖住它
  —— 它只归应用写。
- **旧前缀 `data/raw/` 是遗留**：老结构的库内原始副本在迁移后没有任何身份 —— 不算条目
  （`kbEntryFiles` 与 `index_build` 都整棵跳过 `data/raw/`）、不算原始数据（`kbRawFiles`
  只认 `raw/` 前缀）、应用不改不删它（`kb_entry_delete` 明确拒）。迁移只搬 `kb/`，
  遗留副本留在原地由用户自己处理。
- **本机关联（源头文件夹）只落本机设置**（`kbRawSources` 键不变，类型 `KbSourceLink`，
  形状 `{root, name, dir}`）：它是「添加知识库」时选的那个本机文件夹，是**持续关联**的
  源头 —— 清洗前应用把它的变化复制进 `raw/<名>/`（`kb_source_sync`，只增改不删）。
  没有关联的知识库（别的设备添加的）直接用仓库里的 raw 副本，**只读**：删除文件 /
  清洗文件的入口不出（知识库级的删除与清洗不受限 —— 清洗读仓库里的 raw 就够）。
  关联的规矩沿用：路径不进 theme.json、不参与外观同步；同一文件夹不挂两个名字；
  源头文件夹指到知识库文件夹自己（或包着它）一律不认（复制会自己拷自己）。
- **清洗的硬前置是把原始文件上传远程仓库**（编排全在 stores/kb.ts 的 `startClean` 一条线上）：
  ① **源头同步**（范围内有关联的知识库，`kb_source_sync` 把本机改过的文件带进 raw）→
  有复制就重扫一遍（状态清单以同步后的 raw 为准）→ ② **上传**（`kb_sync`：提交整树 +
  拉回 + 推送）—— 没连远端、推送失败都在这里拦下，不让「本地洗了、远端没有」的状态发生 →
  ③ 算清单（未入库 + 有更新，按范围过滤；没有待洗的就明说）→ ④ 专用 Pi 会话清洗 →
  ⑤ 收尾：重建索引 → **再推一次**（把新条目送上去）→ 刷新。环境的拦路（Node / Pi /
  模型 / 密钥）沿用 AI store 的 envGap 级联，进清洗面板就地说明。
- **添加知识库 = 二次确认后一口气做完**（弹层内翻确认页，不是再叠一个框）：名称 +
  本机源头文件夹 → 确认页写明「复制进 raw → 登记上传 → 立即清洗」→ **不确认就当不
  添加**（一个字不落盘）。所以重名、文件夹冲突、清洗环境缺、没连远端这些拦路都在
  **复制之前**做。弹层只转**本地那几步**（复制 / 清单 / 关联，不到一秒）就关 —— 上传
  是清洗的硬前置，交给清洗的准备阶段（面板逐步可见）；上传失败时本地保留（清单与
  文件都在，重试「同步」能补上），首洗拦下并说明。
- **删除是受控动作，两边一起删**：删知识库 = 删条目（指向该库的全部，不管 raw 在不在）→
  删 `raw/<名>/` 与 `data/<名>/`（`kb_delete_tree`，存在才删）→ 清单移除 → 本机关联移除 →
  重建索引 → 上传；**源头文件夹一个字不动**（确认框写明）。删文件（子文件行右键，仅
  有关联时出现）= 仓库里那份与源头文件夹里那份一起删（`kb_file_delete`；源头持续关联着，
  只删仓库那份会在下一次源头同步时回来）→ 指向它的条目一并删 → 重建索引 → 上传。
  所有删除都弹确认框（AppDialog 挡住、列出将删的条目、说明「永久删除；只有提交过 git 的
  才能从历史恢复」）。
- **「有没有更新」的口径只有一份，在 kb.ts**：条目 frontmatter 的 `source` 与 raw 文件
  配对（带不带 `raw/` 前缀两种写法都认；**知识库名精确**（大小写敏感，跨设备身份键）、
  内层路径按 Windows 口径不敏感），没有条目指向 = 未入库；比较的是**内容指纹**
  （`source_hash` 的 SHA-256 与当前文件），不同 = 有更新；旧条目没有 `source_hash` 时
  回落 mtime。
  **有关联的知识库以本地为准**：`kb_scan` 带着「知识库名 → 本机源头文件夹」的关联清单，
  Rust 顺路对源头文件夹逐文件算 SHA-256（`walk_local`，噪音名单同一条），状态判定时
  **本地这份存在就以本地指纹 vs 条目 `source_hash` 比**（matchKbRawStatus 的 `localFiles`
  参数）—— 本机改了没洗，正是「有更新」要催的事；本地没有这份（没关联 / 本地删了 /
  指纹没算出）才回落仓库副本与条目比。每次重扫仍只对**有条目指向的文件**算仓库侧哈希；
  有关联的知识库每次重扫对源头文件夹整份算哈希（与条目指纹同一档的既定代价，大文件夹
  会变慢）。
  已知取舍：新增的本地文件要等清洗前的源头同步把它带进 raw，才会在清单上出现
  （状态以 raw 行为载体）；直接在源头文件夹里删文件也不会同步进 raw（列表里删文件
  才会两边一起删）。
- **失联条目的清理**：条目还在、指向的 raw 文件不在了（多半是别的设备删了、pull 下来
  后条目还在），知识库行显示「已删除 N」（每次重扫现算的派生值，不落盘）；点开按 raw
  文件分组列出将删的条目，确认后整组删 → 重建索引 → 上传 → 刷新。判定两条同时成立：
  条目的 `source` 解析到**清单里已有的知识库名**、扫描清单里确实找不到这个文件；
  清单里没有的知识库名不判（那种条目按「出处写得不对」处理，不给删除入口）。
  raw 在仓库里，没有「盘不在与被删分不清」的情形 —— 扫描成功而文件不在，就是真的不在。
- **一次性的迁移**（应用做，用户确认后才动手）：旧结构（`kb/` 在、清单没有 → 工具条出
  「迁移」按钮）→ `kb_migrate`：各来源文件夹复制进 `raw/<名>/`（跳过噪音；已存在的文件
  不动）→ `kb/` 整体搬进 `data/`（保留内层结构；撞名如实失败）→ 条目里的 `data/raw/`
  前缀改写成 `raw/`（frontmatter 的 source 与正文里的相对链接同一段写法，一并改对）→
  删旧 `index/` → 写清单（从本机关联造）→ 重建索引 → 上传。**只能迁移一次**
  （`raw/kb.json` 已存在时 Rust 拒绝）。
- **git 全在 sync.rs，与笔记同一条路**：`sync_folder` 是笔记与知识库共用的实现
  （提交 → `pull --rebase --autostash` → 推送，锁 `lock_workflow`、`set_git_auth`、
  `ensure_commit_identity`、busy 拦截、冲突不挑边），两个薄壳：`kb_sync`（提交信息
  `kb: <设备名>`，推整棵工作树）与 `kb_pull`（**只拉不推**）。仓库还是用户自己 clone 的
  —— 应用不 init、不 clone、不改 origin；没仓库 / 没远端时同步与清洗都如实拦。
- **打开页面后台拉一次远端**（`kb_pull`）：列表数据来自远程仓库，pull 下来才有别的设备
  推的东西。拉到了新东西就重扫；失败只把原因摆到同步那行（`syncError`），**打开页面这
  件事不因网络失败变成一页错误**；清洗进行中不拉。这是同一条 kb 仓库出口、只是触发时机
  多了这一处（见 features-and-architecture.md「数据与隐私」）。
- **界面只说原始文件的事**（清洗的数据用户看不懂、也不关心）：条目在应用内没有阅读
  视图 —— 条目清单仍要读（frontmatter 的 source / source_hash 驱动状态判定与失联清理，
  `entries` 是 store 的内部数据），但**任何清洗产物的路径与明细都不上界面**：概览只有
  原始数据的统计与仓库归属（条目数、索引、标签分布全部不摆）；原始查看不摆「N 个条目
  整理自它」；**清洗收据以原始文件计**（store 把 Pi 写下的东西按 frontmatter 的 source
  映射回 raw 层，分「新入库 / 重新入库」两组）；删除确认框只给数量、不列条目路径。
  重建索引**没有手动入口**（应用在每个写点自动重建：清洗收尾、删除、迁移、失联清理），
  概览也没有索引区 —— 工具条没有这颗按钮。
- **巡检（kb-lint.ts）已随条目阅读退役**：没了消费方，孤儿 / 断链那些口径一并删除。
- **清洗的几条硬规矩**（都在 stores/kb.ts 的 startClean 一条线上）：会话 id 用独立的 uuid、
  **不写入 `aiSessions`**（AI 页保持通用控制台），留档照旧落在 `data\pi\sessions\` 可审计；
  权限固定**「完全访问」**（这版 Pi 的 read 读不了目录）；提示词不再列命令禁令，只交代
  分工：git 提交 / 推送归应用、仓库里不留脚本与临时文件；**raw 层一个字不许改**
  （它是清洗的输入，上传归应用）；条目落位跟着原始文件走 —— `raw/<名>/…` 的条目写到
  `data/<名>/…`（同名目录，删除知识库时按目录清得干净），主题目录 `NN-主题名` 在它下面；
  清单**每一行都带「实际文件」**（仓库内的绝对路径）与内容指纹（抄进 `source_hash`）；
  万一真来了确认帧就 `confirmFrame(id, false)` 挡回去；模型与思考档位沿用全局默认，
  **不新增设置**；缺 Node / Pi / 模型 / 密钥时清洗面板就地拦下并给去处，不弹窗。
- **扫描 / 读文件只认仓库内两层，有关联的以本机为准**：`kb_scan` 扫整棵仓库（任意后缀、
  带 `abs`，噪音名单复用 `notes::is_skipped_entry`）、带回清单原文，并顺路对本机关联的
  源头文件夹逐文件算 SHA-256（`links` 参数是「知识库名 → 本机源头文件夹」）；
  `kb_read` / `kb_fingerprints` 只认 `raw/` 与 `data/` 前缀（仓库根下的其他文件不对外读），
  越界一律挡（与 notes.rs 同一条边界，`fs_util::resolve_under` 逐段挡 `..` / 盘符 / UNC）。
  **raw 层的文件有关联且本机有这份时，读的是本机那份**（本机是事实源：路径、修改时间、
  内容、外部打开全落在它上，见 matchKbRawStatus 的本地覆盖）；本机没有 / 文件夹打不开 /
  关联重叠才回落仓库副本 —— 没关联的知识库从头到尾就是仓库副本。
  渲染层不自己拼路径规则。
- **检测是手动的，没有任何后台动作**（除了打开页面那一次 pull）：工具条那颗「检测更新」
  = 重扫一遍（`reload`）+ 把与上一次检测的差报一句（`stores/kb.ts` 的 `detect`）。
  **不做文件监听、不做后台轮询、不做自动清洗**（起子进程花额度、还往库里写文件，不该在
  没人看着的时候发生）。「上一次检测」那几个数只在内存里（`lastDetect`）。
- **清单文件的写口子只有应用**：添加 / 删除知识库时由 store 拼 JSON（`serializeKbManifest`
  收敛：名字 sanitize、去重）经 `kb_config_write` 落盘，Rust 挡一层「必须是合法 JSON」
  （写坏清单等于砸掉列表）。清单认不出的形状（文件不在 / 不是 JSON）**不是错误**：
  按空清单处理，老仓库在迁移前就是这个样子。
- **「像不像知识库」放宽了一档**：清单有、`raw/` 或 `data/`（或旧结构 `kb/`）任一在、
  **文件夹是空的**（第一次用，添加知识库就从这儿开始）都算；一个塞满别的项目文件的
  文件夹不算（那多半是选错了目录）。判定在 stores/kb.ts 的 `looksLikeKb`，测试钉死。
- **应用对条目内容的写仍是清洗这一条路**（外加受控的删除与迁移改写）：条目正文与元数据
  始终是 Agent 写的，应用只编排、写生成物。**不要把「跑仓库脚本」做回来**
  （会引 git 之外的预装程序依赖）。
- **两棵树的口径**：左栏一棵树（知识库行 → 目录 → 文件），由 kb.ts 的 `kbRawTree` 按 rel
  现算（目录在前、同层按名字，与笔记树同一把 collator）；搜索 / 状态筛选是在过滤后的
  清单上再收一次树；展开态只活在组件里不落盘（重扫 / 重建索引会整树重算），左栏宽度住
  theme.json 的 `kbTreeWidth`（与笔记 / 视频 / AI 树同一套做法，见 theme.ts）。
  页面**纵向 flex 三块**（工具带 / 同步报错那行 / 两栏），**行距一律取设置里那一档
  `--card-gap`**；顶部留白不归页面管。两栏的内边距**同一档**（都是 sp-3），右栏阅读视图
  自己**不再补左边距**。
- **frontmatter 解析认最小集合**：与 skills.ts 同一条路数（首行 `---` 围栏、单行键值、
  tags 认 `[a, b]` 列表），多行块标量如实丢掉；解析失败回空值**不是错误**。索引读不到 /
  认不出同样不是错误——条目清单是扫出来的，不依赖索引。
- **索引只由应用生成**：`kb_index_build` 重建 `data/_catalog.md` 与 `data/index.json`，
  格式与既有生成物一致（含 CRLF 换行与那个「由 Workbench 自动生成」文件头；`generated_at`
  由渲染层按本机时区算）；`data/` 还没建（第一次添加、还没洗过）按零条目重建，不是错误。
  改输出格式只改 kb.rs 一处。**别把索引交回给 Agent**：清洗的提示词明令 Pi 不碰生成物。
- **条目之间用相对链接，不用 Obsidian 双链**：`[MuButton](./button.md)` /
  `[xx](../02-主题/xx.md)`（提示词里的契约，条目互链是 AI 检索的织网）。应用内不渲染
  条目正文，链接解析不再归应用管。
- **还没选文件夹那一屏不摆说明**：整页只有一块自绘线稿、「知识库」标题与那颗按钮，居中
  浮在画布上、**不套卡片**（线稿的笔法与 mask 用法照 AI 助手页那一屏来）；仓库该怎么摆
  与清洗那句都收在按钮的悬停里，别在那屏上加回说明书。

## 实现

- 导航栏第六项「知识库」：看一个仓库里 `raw/ + data/` 两层的**纯数据**独立项目。
  工具条从左到右：**添加知识库**（primary）→ 开始清洗 → 同步（v-if canSync）→
  检测更新 → 迁移（v-if migrateNeeded）→ 换文件夹。头部只有标题与位置（统计与
  左栏顶上那排筛选 chips 重复，不摆第二份）。（「打开文件夹」没有工具条按钮 —— 右键菜单的
  「在资源管理器中打开」覆盖了它。）
- **左栏只有一棵树**（顶部 tab 已移除）：知识库行（清单一条一行，带本机关联与否、几个数
  与「已删除 N」按钮）→ 目录 → 文件行（只有「有更新」一个 tag，全栏唯一上色的地方，
  `--st-fail` + `--st-fail-soft`）。状态筛选 chips（全部 / 未入库 / 有更新 / 已入库，带计数）
  在树顶上；筛选时只留有东西的知识库行、整树摊开。三种行都是一行 28px，路径与关联说明
  收在悬停里。空态配图（EmptyState）：还没有知识库（指向「添加知识库」）与筛不出东西两说。
- **右键菜单**（FloatingMenu 外壳，与笔记树同一副）：三种行都有**「在资源管理器中
  打开」**—— 文件用它的 abs（有关联是本机源头那份、没关联是仓库副本，`reveal` 对文件
  是所在目录选中它、对目录是进到里面）；目录按关联落到本机源头的对应子目录（没关联落
  仓库副本的 raw 下）。在此之上：知识库行有清洗知识库 / 删除知识库（danger）；子文件行
  **只有这台机器关联了源头文件夹时**才有清洗文件 / 删除文件（danger）—— 没关联的副本
  只读。
- **右栏互斥三态**：清洗面板（cleanPhase !== 'idle' 时优先）> 原始数据查看（KbRawViewer：
  文本类就地预览、预览不了的给「用系统默认程序打开」，地址用扫描回来的 `abs`）> 概览
  （KbInfoPanel：原始数据统计 / 仓库归属）。原始数据与清洗面板的切换沿用旧口径。
- **添加知识库弹层**（KbAddDialog，AppDialog penetrable）：名称（候选名可点选、
  `kbSourceNameHint` 三态提示：同名拦住 / 大小写不同给精确写法 / 编辑距离 ≤ 2 提醒笔误）+
  源头文件夹（判「同一个文件夹不挂两个名字」）→ 点「添加」翻**确认页**（三步说明 +
  「现在取消的话这个知识库不会被添加」）→ 「确认添加并清洗」才调 store 的 `addLibrary`。
  活儿在跑时按钮转圈（`working`）、弹层不关。
- **清洗范围**：工具条「开始清洗」= 全库；右键菜单 = 单库 / 单文件（`KbCleanScope`，
  清单按范围过滤）。清洗进行中工具条的其余按钮禁用；面板与旧版同一副（状态行 / 实时
  日志 / 取消 / 收据），**收据以原始文件计**：store 把 Pi 写下的条目按 frontmatter 的
  source 映射回 raw 层，分「新入库 / 重新入库」两组，条目路径不出现在面板里。
  **准备阶段（`preparing`）面板先行、逐行打日志**：源头同步 / 重扫 / 上传远程是实打实
  的耗时（上传是三次出网，是「点了到开洗」那几秒的大头），每步一行日志、随时可停
  —— 没有反馈的等待就是「点了没反应」。
- **弹层清单**（全部 AppDialog，挡住不 penetrable）：删除知识库（列条目、源头文件夹不动）、
  删除文件（写明两边一起删 + 条目一并删）、失联清理（按 raw 文件分组）、迁移确认（四步
  说明 + 遗留副本不动 + 只能一次）。换页不关弹层。
- **读是只读的，写全是受控动作**：命令十二条 —— `kb_scan`（平铺清单 + 清单原文 + 源头
  文件夹指纹，`links` 参数是「知识库名 → 本机源头文件夹」）、
  `kb_read`（只认 raw/ 与 data/）、`kb_fingerprints`、`kb_index_build`（`data/` 没建按零
  条目建）、`kb_entry_delete`（只删 `data/` 下 `.md`，排除 `_catalog.md`、拒 `data/raw/`）、
  `kb_source_sync`（源头 → raw，只增改不删；源头与仓库重叠拒）、`kb_delete_tree`（两层
  一起删）、`kb_file_delete`（仓库 + 源头两边删；dir 空串 = 没有关联只删仓库）、
  `kb_config_write`（写清单，挡非法 JSON）、`kb_migrate`（一次性迁移）、`kb_sync` / `kb_pull`
  （sync.rs 的两个薄壳）。路径越界由 kb.rs 逐段挡（与 notes.rs 同一条边界）。
- **建一次索引就是首页活跃度里的一笔**（来源 `kb`，记在 `workbench/kb.ts` 的 `kbIndexBuild`
  里、命令成功之后）—— 调用点是清洗收尾、删除（知识库 / 文件 / 失联清理）与迁移，
  见 [home.md](home.md)。
- **重扫是串行的、旧的会被丢弃**：每一轮带一个序号（`reloadSeq`），回来晚的那轮不覆盖
  新结果。自动 pull 完成后的重扫走同一条路。
- **本机关联变了不整页重扫**：`linkShape` watch 只把列表行重算一遍（行的 dir / 计数跟着
  变），文件与条目没变就不用扫盘。

## 涉及文件

```
  src/kb.rs             知识库（仓库里 raw/ + data/ 两层，布局常量与口径在 packages/kb/src/kb.ts）：
                        扫描（平铺清单 + 清单 raw/kb.json 原文；**任意后缀**；噪音名单复用
                        notes::is_skipped_entry）、读文件文本（只认 raw/ 与 data/）、
                        内容指纹（SHA-256，读不到的跳过）、以及受控写动作：
                        源头同步（source_sync：源头 → raw/<名>/，只增改不删、噪音跳过、
                        与仓库重叠拒）、删知识库（delete_tree：raw/<名>/ + data/<名>/）、
                        删文件（file_delete：仓库 + 源头两边删）、写清单（config_write：
                        挡非法 JSON）、一次性迁移（migrate：复制来源 → kb/ 搬 data/ →
                        data/raw/ 前缀改写 → 删旧 index/ → 写清单，只能一次）、
                        重建索引（data/_catalog.md + data/index.json，CRLF，data/ 没建
                        按零条目）、删条目（只删 data/ 下 .md，排除 _catalog.md 与
                        遗留 data/raw/）。「有没有更新」「哪些是条目」这些口径都在渲染层的
                        纯函数里；条目内容由清洗的 Pi 写（编排见 stores/kb.ts，驱动链路见 src/ai.rs）；
                        git 的提交 / 拉推在 sync.rs（sync_folder 共用实现 + kb_sync / kb_pull）
```

渲染层两处（原注解）：

```
    kb.ts（知识库：扫清单（带清单原文）/ 读文件 / 内容指纹 / 重建索引 / 删条目 /

           git 通道；仓库探测复用笔记那条通用通道）
    kb.ts                知识库：扫出来的清单拆成条目 / 原始数据 / 索引，清单文件解析成

```
