# 知识库（kb）

知识库（kb）的文档：先读「约束」一节（不能破的规矩）；「实现」一节装为什么这么做、踩过哪些坑。
跨模块的通用事实（导航壳层、数据与隐私、目录结构）见
[features-and-architecture.md](../features-and-architecture.md)，跨模块红线见 [AGENTS.md](../../AGENTS.md)。

## 约束

关键落点：`packages/kb/src/kb.ts`（布局常量、frontmatter 解析、状态判定、本机日期，带单测）、
`packages/kb/src/kb-clean.ts`（**清洗提示词**：应用内的资产，不对外提供、开发期迭代，带单测）、
`apps/desktop/src-tauri/src/kb.rs`（扫描、读文本、**重建目录与索引**）、`apps/desktop/src/renderer/src/workbench/kb.ts`（适配）、
`apps/desktop/src/renderer/src/stores/kb.ts`（编排 + 清洗的全程驱动）。AI 那条驱动链路见 [ai.md](ai.md)。

- **仓库是纯数据，条目内容不由应用写**：知识库仓库（如 `E:\muyian\agent`）里没有脚本、
  没有 Agent 说明文件 —— 只有 `kb/`（条目）、（可选的）`data/raw/`（原始资料）与两个生成物。
  清洗由应用**全程编排**：扫描出的待处理清单拼进 kb-clean.ts 的提示词，交给内置的 Pi
  （走 ai.rs 的通用驱动链路），跑完应用自己重建索引、刷新状态。条目的正文与元数据始终是
  Agent 写的，应用只编排、外加写生成物。除重建索引外不要再加写动作，
  **也不要把「跑仓库脚本」做回来** —— 那等于承认仓库里该有脚本，还得引 git 之外的预装程序依赖。
- **清洗的几条硬规矩**（都在 stores/kb.ts 的 startClean 一条线上）：会话 id 用独立的 uuid、
  **不写入 `aiSessions`** —— AI 助手页那棵树认的是设置里的清单，清洗会话不进树（AI 页
  保持通用控制台，与知识库无关），留档照旧落在 `data\pi\sessions\` 可审计；权限固定
  **「完全访问」**（这版 Pi 的 read 读不了目录，不给 bash 它连清单里的文件都找不全）——
  提示词不再列命令禁令，只交代分工：git 提交 / 推送归应用、仓库里不留脚本与临时文件；
  **来源文件夹里的资料一个字都不许改 / 不许移动 / 不许删除**（那是用户自己的原文，
  早先 raw 是库里的副本、写坏了 git 里还有一份，现在不是了 —— 这一条只有提示词守着，
  权限档不会拦写操作，所以它必须一直留在提示词里）；清单里带「实际文件」时读那个绝对路径
  （资料在库外），条目 source 照旧写逻辑路径；万一真来了确认帧就 `confirmFrame(id, false)`
  挡回去，不让流程吊死；模型与思考档位沿用全局默认（`aiDefaultProvider / aiDefaultModel /
  aiThinking`），**不新增设置**；缺 Node / Pi / 模型 / 密钥时清洗面板就地拦下并给去处，
  不弹窗。提示词改了想看效果就跑一轮真实清洗 —— 那就是它的测试（外部来源能不能读、
  有没有碰来源文件，都得靠它验）。
- **原始数据的最外层是「来源」，配置只是一层映射**（`kbRawSources`，形状与收敛在 kb.ts 的
  `KbRawSource` / `sanitizeKbRawSources`）：`data/raw/<来源名>` 那一格对到本机一个文件夹。
  **逻辑路径不随来源实际在哪儿变** —— 条目的 `source`、正文里指向原始资料的相对链接、
  状态配对、巡检全都按 `data/raw/<来源名>/<内层>` 走，来源换位置不用改任何条目。
  三条要一直守住的：**应用不搬运 / 不复制 / 不删除任何文件**（「移除来源」只删这条配置）；
  **配置只落数据文件、只对本机成立**（每条带 `root`，来源名在不同知识库里可以重名；
  不进 theme.json、不参与外观同步）；**名字定了不给改名**（它是条目 source 的契约，
  换名走「移除 + 重新添加」）。
- **库里那份 `data/raw/` 是兼容层**：没配来源的名字照旧读库里那份（老库与老副本平滑过渡），
  同一个名字配了外部路径时**以映射为准**、库里那一棵整棵不列（`kbVisibleRawEntries`），
  来源行上会说明「以映射为准」（`shadowed`）—— 删不删那份副本由用户自己决定。
  路径打不开（盘不在 / 被改名）的来源只报它自己那一条（Rust 的 `sources[].error`），
  别的来源与整页照常。
- **仓库布局是两边的约定，改要一起改**：`data/raw/`（原始资料投放区，也是逻辑路径的名字空间）、
  `kb/`（条目，`_catalog.md` 不算条目）、`index/index.json`（生成物）这几个常量在
  [kb.ts](../../packages/kb/src/kb.ts)，与知识库仓库自己的 README 是一套说法；用户挑的文件夹
  认不出 `kb/`、`data/raw/` 与已配的来源中的任何一个时，页面明说「不像知识库」，不硬扫。
- **检测是手动的，没有任何后台动作**：工具条那颗「检测更新」= 重扫一遍（`reload`）+
  把与上一次检测的差报一句（`stores/kb.ts` 的 `detect`）。**不做文件监听、不做后台轮询、
  不做自动清洗** —— 清洗永远是另一颗按钮、由用户点出来（起子进程花额度、还往库里写文件，
  不该在没人看着的时候发生）。「上一次检测」那几个数只在内存里（`lastDetect`），
  不落盘、不进设置 —— 它是「上次报给你的话」，不是数据事实。
- **扫描与读文件都要带上来源清单**：`kb_scan` / `kb_read` 的 `sources` 参数就是那份映射
  （`{name, dir}`），由 Rust 在各自来源根内逐段挡越界（与笔记同一条边界：渲染层只能报
  「来源名 + 文件夹」，文件那一截不能自己拼）。每条扫描结果带 `abs`（真实绝对路径）——
  打开文件、清洗清单里给 Pi 的地址都用它，**渲染层不自己拼路径规则**。
- **「有没有更新」的口径只有一份，在 kb.ts**：条目 frontmatter 的 `source` 归一化后与 raw
  文件配对（带不带 `data/raw/` 前缀两种写法都认、大小写不敏感），没有条目指向 = 未入库；
  原始文件比指向它的条目里**最新**那份的 mtime 还新 = 有更新。它依据文件修改时间，是启发式
  （git 操作会重写 mtime）——要换口径只改 kb.ts 一处，别在组件里另拍一份。
- **巡检的口径只一份在 kb-lint.ts，但界面上不展示**：孤儿（除导航页 `README.md` 外没有
  条目链接它）、断链（正文里的站内链接解析不出库里的文件）、元数据缺项、出处指不到文件、
  主题目录不合 `NN-主题名`；名称（`KB_ISSUE_LABELS`）与顺序（`KB_ISSUE_KINDS`）也在
  [kb-lint.ts](../../packages/kb/src/kb-lint.ts)，store 每次重扫照旧算一遍（`stores/kb.ts`
  的 `lintIssues`）。**概览只留统计 / 标签 / 索引 / 仓库** —— 这张清单曾经摆在概览里，
  按「对一篇一个条目、彼此不提及的库恒定是满值，没有信息量」去掉的（用户定的）。
  **不要为它新增写动作** —— 它只报事实，写的口子照旧只有重建索引那一处。
- **条目之间用相对链接，不用 Obsidian 双链**：`[MuButton](./button.md)` /
  `[xx](../02-主题/xx.md)` —— 工作台与 Obsidian 都认相对链接，`[[ ]]` 只有后者认
  （markdown-it 会把它当普通文本渲染出来）。解析口径（相对谁、什么算跳不到库里）在
  kb-lint.ts 的 `resolveKbLink`；正文链接在扫描时一次读进 `KbEntryMeta.links`，巡检与
  站内跳转都不再读文件。MarkdownView 的 `internalLinks` 是那个口子（**默认关**，只有条目
  阅读打开它）：纯锚点（`#某一节`）不往上交，外部地址照旧走 `openExternal`。
- **清洗的收据分「新建 / 覆盖」**：拿跑之前那份条目清单（store 的 `cleanBefore`）与 Pi
  报出的写入路径比，口径在 kb-clean.ts 的 `splitCleanWrites`（只认 `kb/` 下的 `.md`，
  `_catalog.md` 是生成物不算条目）。界面把条目名做成可点的按钮 —— 点一下收起面板去读那一条
  （收面板与「返回概览」同一条路，收据跟着这一轮的日志走）。
- **应用对条目仍然只读**（巡检与收据都不破这条）：条目的编辑只有清洗这一条路 —— 改内容去
  raw 源头再洗一轮；应用自己写的只有 `_catalog.md` 与 `index.json` 两个生成物。
- **两棵树都是目录结构**：左栏「条目 / 原始数据」两签的树分别由 kb.ts 的 `kbEntryTree` /
  `kbRawTree` 按 rel 现算（目录在前、同层按名字，与笔记树同一把 collator），搜索 / 状态筛选
  是在过滤后的清单上再收一次树；展开态只活在组件里不落盘（重扫 / 重建索引会整树重算），
  左栏宽度住 theme.json 的 `kbTreeWidth`（与笔记 / 视频 / AI 树同一套做法，见 theme.ts）。
  页面**纵向 flex 三块**（工具带 / 同步报错那行 / 两栏），**行距一律取设置里那一档
  `--card-gap`** —— 报错那行是 v-if 的，flex 里它不渲染就不占高度也不占行距（早先的三行网格
  把它钉在第二行，于是工具带与两栏之间白白多出一条行距，看着比别的页空一截）；顶部留白不归
  页面管（同 global.css「顶栏与内容之间那条缝」）。两栏的内边距**同一档**
  （`.kb-view__left` / `.kb-view__right` 都是 sp-3），右栏那两个阅读视图（条目 / 原始数据）
  自己**不再补左边距** —— 那会让标题与正文比左边那棵树多缩进一层（`.panel` 默认的 sp-4
  也跟着这一档收窄）。
- **frontmatter 解析认最小集合**：与 skills.ts 同一条路数（首行 `---` 围栏、单行键值、tags 认
  `[a, b]` 列表），多行块标量如实丢掉；解析失败回空值**不是错误**（没有元数据的条目照样列出，
  标题回落文件名）。索引读不到 / 认不出同样不是错误——条目清单是扫出来的，不依赖索引。
- **索引只由应用生成**：`kb_index_build` 重建 `_catalog.md` 与 `index.json`，格式与既有
  生成物一致（含 CRLF 换行与那个「请勿手改」的文件头 —— 头部写的是「由 Workbench 自动生成」）；
  `generated_at` 由渲染层按本机时区算（`todayIsoDate`）。改输出格式只改 kb.rs 一处，
  内容断言在 kb.rs 的测试里。**别把索引交回给 Agent**：清洗的提示词明令 Pi 不碰生成物，
  索引归应用自己重建（它要的是「谁跑的结果都一样」）。
- **同步与仓库探测复用笔记那两条通道**（`note_sync` / `note_repo_state`，本来就是
  「对任意文件夹、认它自己的 origin」的实现）：不新增 git 命令包装、不新增凭据机制；
  知识库文件夹自己有 `.git` 且连了远端时同步按钮才出现，**只有点同步才出网**（推的是
  知识库仓库自己的 origin，应用不 init、不改 origin）。扫描与读文本本身不出网；
  清洗走的出网就是 AI 助手那一条（用户自己配的端点），不新增出口。
- **条目在应用内只读不编辑**：右栏用 MarkdownView 渲染（工作日志同款的安全口径）。
  条目会被清洗覆盖（raw 是唯一事实源，重洗时保留 created、更新 updated），在应用里开
  编辑口子会让人改了白改 —— 改内容去 raw 源头，再清洗一轮。原始数据的查看同样只读：
  看法（渲染成正文 / 纯文本预览 / 交给系统默认程序）由 kb.ts 的 `kbRawViewKind` 按后缀
  一处分类，外部打开走**既有的 `open_path` 通道**（快捷启动同款，不新增 Rust 命令；
  按文件关联打开本机文件，不算出网），地址用扫描回来的 `abs`（来源里的资料在库外面）；
  条目与原始数据的查看互斥，右栏同一时刻只有一份。
- **还没选文件夹那一屏不摆说明**：整页只有一块自绘线稿、「知识库」标题与那颗按钮，居中浮在画布上、
  **不套卡片**（`.guide` 在纵向 flex 里 `flex: 1 1 auto`，它才吃得到整页高度；线稿的笔法与 mask
  用法照 AI 助手页那一屏来 —— 1px 描边、`--ink-3`、0.55 不透明度、200 宽，别换成图标库里的图标）；
  文件夹该怎么摆（`kb` 与 `data/raw`，以及外部的来源文件夹）与清洗那句都收在按钮的悬停里
  —— 与 AI 助手页同一条语气（见 [ai.md](ai.md)），别在那屏上加回说明书。

## 实现


- 导航栏第六项「知识库」：看一个用户在别处维护的**纯数据**独立项目（没有脚本、没有 Agent 说明文件），
  读是只读的，写只有一处（重建索引）—— 条目内容由应用编排的清洗写成：这一页算清「哪些没入库、
  哪些又更新了」，交给内置 Pi 按应用内提示词整理（用户不写指令、看不到提示词）。
  选的文件夹里 `kb`、`data/raw` 与已配的来源一个都认不出来时明说「这看起来不是知识库」
- **还没选文件夹时整页只有一块自绘线稿、标题与按钮**（居中、**不套卡片**）：线稿是三张叠着的纸
  （前一张是收好的条目、后两张散页，1px 描边、`--ink-3`、0.55 不透明度、200 宽；后面两张用 mask
  裁掉被盖住的部分）。文件夹长什么样收在按钮悬停里 —— 与 AI 助手页同一条语气
  （见[「AI 助手（ai）」](ai.md)）
- **知识库文件夹是用户挑的目录**（`kbDir`，与笔记 / 技能互不相干），布局常量在
  [shared/kb.ts](../../packages/kb/src/kb.ts)：`data/raw/` 投放区、`kb/` 条目（frontmatter 的
  `source` 指回原始文件）、`index/index.json` 机器可读索引；`_catalog.md` 是生成的全库目录，不算条目
- **原始数据的来源**（左栏「原始数据」签最外层那一格）：`data/raw/<名字>` 这一格可以在界面上
  配到本机一个文件夹（来源行尾那颗齿轮 / **左栏顶上那一行右端**那颗「添加原始数据」——
  只有原始数据这一签才摆它，且是一颗没有底色的图标按钮，弹层是
  [KbRawSourceDialog.vue](../../apps/desktop/src/renderer/src/components/KbRawSourceDialog.vue)），
  配过之后就不必再把资料 copy 进库里。扫描时按来源名把外部文件夹里的文件挂到**逻辑路径**
  `data/raw/<名字>/…` 下（[kb.rs](../../apps/desktop/src-tauri/src/kb.rs) 的 `walk_into` 收前缀），
  所以原来那套口径（source 配对、站内跳转、巡检）一个字都不用改。来源行有三种样子：
  `mapped`（配了外部文件夹）、`inRepo`（没配过，读库里那份）、`unconfigured`（配过但没路径 ——
  给它再指定一次就是走同一个弹层）；路径打不开时原因落在那一行上，别的来源照扫。
  「移除来源」只删配置：库里那份副本、来源文件夹里的东西一个都不动
- **读是只读的，写只有一处**：命令就三条 —— `kb_scan`（平铺清单、**任意后缀**，噪音名单复用
  `notes::is_skipped_entry`；带 `sources` 参数与 `abs` 字段）、`kb_read`（`data/raw/<来源名>/…`
  经来源根解析）、`kb_index_build`。条目内容不由应用写（写它的是清洗请来的
  Pi）；口径都在 shared/kb.ts 的纯函数里，路径越界由 `kb.rs` 逐段挡（与 notes.rs 同一条边界，
  报错说「知识库文件夹」／「来源文件夹」所以那一小段代码是它自己的）
- **「有没有更新」是 mtime 启发式**：source 归一化后与 raw 配对（带不带前缀都认、大小写不敏感、
  `/` 与 `\` 等价）—— 没条目指向 = 未入库；原始文件比指向它的条目里最新那份还新 = 有更新；
  否则已入库。git 操作会重写 mtime（已知的不精确）；换口径只改 shared/kb.ts 一处
- **检测更新**（工具条那颗）：`detect()` = 重扫 + 按上一次检测的几个数报一句差
  （没变化就明说「没有变化」，静默什么都不说等于让人怀疑按钮没生效）。**只有这一条路**：
  没有文件监听、没有后台轮询、没有自动清洗（要不要洗永远由用户点）
- **清洗（一键，应用全程编排）**：「开始清洗」把待处理清单拼进提示词，起一条**专用 Pi 会话**，
  跑完自动重建索引、刷新状态。提示词是应用内资产（[shared/kb-clean.ts](../../packages/kb/src/kb-clean.ts)，
  带单测）：条目格式契约与做法要求都写死在里面，迭代发生在开发期。**清单每行给两个地址** ——
  逻辑路径（source 写它）与实际文件（来源在库外时读它），另有一条硬禁令「来源文件夹里的文件
  一个字都不许改」。清洗不进 AI 页会话树（不写入
  `aiSessions`，留档照旧在 `pi/sessions/`）；权限固定**「完全访问」**（这版 Pi 的 read 读不了目录），
  真来了确认帧自动挡回并记日志；模型与思考沿用全局默认，缺模型 / 密钥给「打开模型管理」
  （复用 AiModelDialog）。清洗进行中工具条的重建索引 / 同步 / 检测更新 / 换文件夹禁用；
  **收据在面板底部**：写入路径按跑前那份条目清单分成**新建**与**覆盖**（`splitCleanWrites`：
  只认 `kb/` 下的 `.md`），条目名可点 —— 收起面板直接去读那一条
- **索引状态与重建**：`index.json` 读得出就显示生成日期与收录数，与实际条目数对不上提示
  「索引待重建」，工具条**「重建索引」**就地重算。索引只由应用生成（格式与既有生成物一致，
  连 CRLF 都跟着）；读不到 / 认不出不是错误，条目清单是扫出来的
- **条目只读阅读**：左栏「条目」签是按目录结构收成的树（`kbEntryTree` 现算），带搜索
  （标题 / 标签 / 摘要 / 路径，过滤后再收树、整树摊开）；右栏 MarkdownView 渲染
  （markdown-it、`html: false`），头部摆状态、更新日期与出处。**站内链接点得动**：条目相对路径互链
  （清洗提示词要求第一次提到已有条目就链上），点一下就地跳 —— 链到原始资料上照样跳进原始数据查看
  （口径在 kb-lint.ts 的 `resolveKbLink`；`internalLinks` 这个口子只有条目阅读打开）。应用内
  **不提供编辑**：raw 是唯一事实源
- **巡检（只读，算而不显）**：孤儿 / 断链 / 元数据缺项 / 出处指不到文件 / 主题目录不合
  `NN-主题名` 五类（判法在 kb-lint.ts，纯函数带单测），store 每次重扫算一遍，**不改任何
  文件**。**界面不再展示这张清单**（曾经摆在概览最下面，用户按「对我的库没信息量」去掉的）：
  **生成物与主题总览的链接不算引用** —— 「孤儿」的实质是「条目之间还没织网的个数」，
  靠 README 当目录的库天然全是孤儿。出处指到**没收成的来源**里时说的是
  「来源还没指定路径 / 打不开」，不是「条目写错了」
- **同步复用笔记那两条通道**（`note_sync` / `note_repo_state` 本来就是「对任意文件夹、认它自己的
  origin」）：文件夹自己有 `.git` 且连了远端时同步按钮才出现；**只有点同步才出网**
- 页面结构：左栏顶上那一行是「条目 / 原始数据」两签（**添加来源在它的右端，只有原始数据这一签
  才出现**），两签都是按目录收成的树，原始数据签带状态筛选 chips；**三种行都是一行**（同高）：
  来源行是名字 + 要催的状态
  （打不开 / 还没指定路径）+ 这一来源的几个数，路径与「库里那份还在不在」这些说明收在悬停里
  （长绝对路径在窄栏里只会被截成半截，两行块在这一层只是噪音）；**文件行只有名字与一个
  「有更新」tag** —— 已入库 / 条目数 / 后缀 / 时间都不上行（右栏一看就有，分档交给 chips），
  那个 tag 是全栏唯一上色的地方（`--st-fail` + `--st-fail-soft`，与项目卡那些「要催」的 pill
  同一档；它就是要动手的信号，不是错误），
  右栏默认概览（统计 / 标签分布 / 索引状态 / 仓库归属），点开条目切阅读、点开原始文件切查看
  （文本类就地预览，预览不了的给「用系统默认程序打开」；清洗进行中或刚收场时切清洗面板 ——
  标题一行状态 + 实时日志 + 取消，清洗入口只有工具条那一颗「开始清洗」）。
  左右分栏、缝可拖（PanelResizer），宽度住 `kbTreeWidth`
